## 1. 它到底是个什么游戏

### 1.1 四个角色，四种武器手感

不是换皮，是四套投射物逻辑：

| 角色 | 武器 | 机制 |
| --- | --- | --- |
| DeepSeek | 思维链 | 直线穿透，攻击随距离衰减极小，适合拉一条线清场 |
| GPT | 多路采样 | 开局三向散射，覆盖面广、单发偏弱，越近越疼 |
| Claude | 完形环绕 | 自带环绕轨道体，贴身接触即伤，近战最安全 |
| Gemini | 双子回旋 | 投射物飞出后折返，同一发造成两次伤害 |

### 1.2 核心机制一：上下文窗口

拾取 token 会填充「上下文条」（`CTX_MAX = 100`，每点 token 填 2.0）。**填满就进入「溢出」状态**：

- 你：伤害 ×1.55、暴击 +15%
- 敌人：移速 ×1.30、伤害 ×1.22
- 屏幕上会亮起红色暗角 + 噪点带，顶部一条警示横幅
- 溢出期间每秒烧掉 13.5 点上下文（约 7.4 秒），烧完的瞬间释放一次冲击波（90 + 加成伤害、半径 330），并给你 2.2 秒无敌 + 回血 8%

<img src="/tupian/posts/%E7%94%A8AI%E5%81%9A%E4%B8%AA%E5%89%B2%E8%8D%89%E5%B0%8F%E6%B8%B8%E6%88%8F-%E5%A4%8D%E7%9B%98%E4%B8%8E%E5%8F%8D%E6%80%9D/03-overflow.webp" alt="03-overflow" style="width:40%;">

这是整个项目里我最喜欢的设计：它把「变强」和「变危险」绑在同一个动作上，玩家会主动去踩那个临界点。

### 1.3 核心机制二：采样温度

按 `E` 在三档之间循环：

| 档位 | 伤害 | 攻速 | 散射 |
| --- | --- | --- | --- |
| 低温 T=0.2 | ×1.38 | ×0.86 | ×0.45（更集中） |
| 标准 T=1.0 | ×1.0 | ×1.0 | ×1.0 |
| 高温 T=1.8 | ×0.74 | ×1.40 | ×1.85 且 +1 投射物 |

### 1.4 核心机制三：世界地形

六种地形：**两种纯阻挡**（节点、墙）、**两种可交互障碍**（方尖碑会放电，词元簇可撞碎）、**两种区域效果**（池、晶格，能直接走进去）：


<img src="/tupian/posts/%E7%94%A8AI%E5%81%9A%E4%B8%AA%E5%89%B2%E8%8D%89%E5%B0%8F%E6%B8%B8%E6%88%8F-%E5%A4%8D%E7%9B%98%E4%B8%8E%E5%8F%8D%E6%80%9D/05b-terrain-grid.webp" alt="05b-terrain-grid" style="width:40%;">


| 地形 | 阻挡 | 机制 |
| --- | --- | --- |
| 数据节点 `node` | ✓ | 纯阻挡，六边形 + 旋转数据环 |
| 数据墙 `wall` | ✓ | 纯阻挡，面板 + 侧面厚度 + 扫描线 |
| 提示词方尖碑 `obelisk` | ✓ | 每 4.2~6.4 秒释放冲击波，沿环带推开并减速敌人 |
| 词元簇 `cluster` | ✓ | 被撞到逐块碎裂，**每碎一块掉 1 个 token** |
| 潜空间池 `pond` | ✗ | 玩家 ×1.28 速、敌人 ×0.6 速 |
| 注意力晶格 `lattice` | ✗ | 每 2.6 秒脉冲，灼伤区域内敌人（玩家免疫） |

一个刻意的取舍：**玩家子弹可以穿过地形，敌人子弹会被地形吸收**。挡怪不挡我，割草手感才不粘。

## 2. 技术栈：没有引擎，没有依赖，没有构建

```
index.html ── 9 个 <script> 顺序加载 ── 一张 <canvas> + 七个 DOM 覆盖层
   │
   ├─ config.js    全部数值：世界/角色/敌人/关卡/技能/BOSS 阶段（声明式数据，386 行）
   ├─ core.js      U 工具、Assets 预加载、Input、Sfx、Camera、Storage、PERF 性能档
   ├─ meta.js      算力币、永久升级、存档（398 行）
   ├─ entities.js  Player / Enemy / Boss / Projectile / Token / Particle / Agent（1339 行）
   ├─ terrain.js   6 类地形的行为与绘制（638 行）
   ├─ skills.js    升级三选一
   ├─ game.js      主循环状态机、生成、碰撞、渲染、阶段推进（1450 行）
   ├─ ui.js        DOM 界面（835 行）
   └─ main.js      boot、rAF、生命周期兜底
```

### 2.1 为什么故意不用 ES Module

为了让 `file://` 双击就能跑——不用起服务器、不用担心 CORS。这个取舍在 demo 阶段非常值：把文件夹发给任何人，双击就玩。

代价是所有东西都是裸全局（`const CFG`、`const U`、`const Sfx`…），没有模块边界、没有依赖声明，**加载顺序错了就是白屏**。而且 `main.js` 里 `UI.init(game)`、`game.js` 里直接调 `UI.showBossBar()`，双向耦合。

### 2.2 主循环：经典得不能再经典

```js
function loop(now) {
  requestAnimationFrame(loop);
  let dt = (now - lastT) / 1000;
  lastT = now;
  if (dt > 1.0 && game && game.vw) game.forceRepaint();  // 从后台回来，重建画布
  if (dt > 0.05) dt = 0.05;                              // 钳制，防穿模
  try {
    game.applyResize();   // 尺寸变更必须在 render 之前落地
    game.update(dt);
    game.render();
  } catch (err) { showFrameError(err); /* 画一层安全底色，别永久黑屏 */ }
}
```

没有 ECS、没有固定步长物理、没有系统调度器。割草游戏对时序不敏感，`dt` 钳到 50ms 已经足够稳。

### 2.3 数据驱动：`config.js` 是唯一的数值真相

所有可调数值集中在一个文件里，`STAGES` / `CHARACTERS` / `ENEMY_TYPES` / `SKILLS` / `BOSS_PHASES` 全是声明式数组，逻辑代码只读不写。加一关、加一个技能，理论上只动 `config.js`。

难度曲线就是两行：

```js
SPAWN_BASE: 1.55,      // 初始每秒生成数
SPAWN_GROW: 0.078,     // 每秒生成数的增长系数
MAX_ENEMIES: 420,
```

等级曲线是 `FIRST_LEVEL_XP: 6` + `XP_CURVE: 1.26`。六个关卡的差别只是 `spawnMul 0.85→1.6`、`hpMul 0.55→2.8`、`bulletMul 0.7→3.0` 这类倍率。

### 2.4 渲染：Canvas 两趟变换 + DOM 做 UI

- **世界层**：`ctx.setTransform(dpr*zoom, 0, 0, dpr*zoom, ...)`，画地形、敌人、弹幕、粒子、浮动伤害字。
- **屏幕层**：`ctx.setTransform(dpr, 0, 0, dpr, ...)`，画扫描线、数据雨、glitch 条、溢出暗角、小地图、摇杆。
- **UI 全是 DOM**：`#menu` / `#hud` / `#levelup` / `#upgrade` / `#pausePanel` / `#gameover` / `#loading` 七个覆盖层，`css/style.css` 1342 行。

`zoom` 的算法值得一提：不用固定倍率，而是按**屏幕短边要看到多少世界单位**来算，因为竖屏瓶颈是宽度、横屏瓶颈是高度，用短边才能让两种姿态都真的看得见东西。

### 2.5 音效：零音频文件

`Sfx` 用 WebAudio 程序化生成：`tone()` 起一个 `OscillatorNode` + 指数衰减 `GainNode`，`noise()` 现填一段随机 buffer 过带通滤波。`shoot/hit/kill/pickup/hurt/levelup/boss` 各是一组参数。

整个游戏的声音就是几声方波和噪声——这在第 5 节会被算成一笔账。

### 2.6 工具链：Python + Node 脚本

项目里唯一算得上「工具链」的是 `tools/` 下这批脚本，它们才是真正干了引擎该干的活：

| 脚本 | 作用 |
| --- | --- |
| `prep_assets.py` | Pillow/numpy 批量压缩、转格式 |
| `split_hero.py` / `build_rig.py` | 512×512 立绘切件：腿 / 身体 / 头 / 闭眼帧 |
| `compose_blink.py` | AI 生成闭眼整图 → 缩放对齐 → 环带模板匹配 → 羽化遮罩只贴眼睛区域 |
| `check_rig.py` | 分层 alpha 合成后与原图比对，并跑 WebP 压缩误差基线 |
| `build_dist.py` | 只拷运行时文件到 `dist/`，扫描 `assets/*` 引用，缺包就报错退出 |
| `build_tt.py` | webp → 256 色量化 PNG、`config.js` 后缀改写、生成抖音小游戏配置 |
| `verify_*.js` / `diag_*.js` | CDP 设备仿真、像素探针、逐帧截图、实战 bot |

> 这张表后来成了我最不舒服的一处自我审视：**工程质量里最好的部分，恰恰不是产品代码，而是验证脚本。**

## 3. 一周的时间线

真实日期，来自项目里的开发日志。

### Day 1（10-07）：把「能跑」做出来

- 定世界观、写 `config.js` 数据结构、手写主循环、四角色四武器
- 两张 AI 立绘当作角色卡，先跑通「走位 + 自动开火 + 拾取 + 升级三选一」
- 第一次踩到 AI 生图的坑（见 4.1）
- 当天结束：能玩，但只有一关、一种地形、没有 BOSS

### Day 2（10-08）：一天里塞进去半个游戏

这一天是整周最疯的：

- **上午**：把 512×512 立绘拆成「腿 / 身体 / 头」三层，接上走路 + 眨眼（见 4.5、4.6）
- **中午**：地形从 2 种扩到 6 种，加上「上下文窗口」和「采样温度」两套机制
- **下午**：手机适配（双摇杆、安全区、横竖屏布局）、PWA、全屏、发布上线
- **傍晚**：修「人物突然消失」（见 4.2、4.3）、视野放大、加小地图
- **晚上**：关卡系统重做（清怪 → BOSS 阶段状态机）、修 BOSS 弹幕性能

### Day 6（10-13）：局外成长与平台调研

> 中间隔了几天，不是连续开发——这也是 AI 辅助开发的典型节奏：**想起来就补一块功能**。

- 算力币 + 永久升级面板（10 项全局 + 角色专属）
- 抖音小游戏迁移调研：量了包体积、算了改造量、写了完整方案
- 升级入口从底部按钮改成右上角悬浮球

### 之后

没有了。

**这就是问题：游戏在第二天就已经「功能完整」，剩下的时间全在加东西和修兼容。** 没有任何一天是用来回答「它好不好玩」的。

## 4. 八个真实的坑（每个都有截图或数据）

按「问题 → 怎么定位 → 结论」记。这些都是当时写进日志的实测结果，不是事后总结的常识。

### 4.1 AI 生图能出图，但管线不可控

- **工具层**：图像生成不支持 AVIF 输入，必须先转 PNG；并行生成时 `output_dir` 偶尔不生效；同一秒提交的任务**文件名会撞车互相覆盖**，生成后必须核对落盘位置。
- **原画不适合做动画**：512×512 立绘是 3 头身，小腿+鞋只占 y≈398~450（约全高 11%），大腿被裙摆全遮住；单只眼约 57×43px，占脸宽约 40%。

第二条直接判了两个方案的死刑：**绑了骨骼走路也看不清**，而程序化「填肤色画眼线」做眨眼像贴了块创可贴（那版被我自己否掉了，产出文件根本没接进游戏）。

### 4.2 给 `canvas.width` 赋值会立刻清空画布——连赋同一个值也会

手机端地址栏收起/展开会频繁触发 `resize`。原来的 `resize()` 直接写 `canvas.width = vw * dpr`。如果这次清空发生在 `render()` 之后、浏览器 paint 之前，那一帧就是全黑——看起来就是**「人物突然消失」**（其实是整屏黑一帧，只是人最显眼）。

左图正常，右图是同一位置黑掉的那一帧：

| 正常 | 掉帧黑屏 |
| --- | --- |

**定位方法比结论更值钱**：先 `render()`、采样画布中心一个像素，再调用尺寸未变的 `resize()`、再采样，得到 `[145,113,34,255] → [0,0,0,0]`，当场坐实。

在此之前我走了两条弯路：

1. 怀疑精灵层漏画，包了 `drawImage` 计数——第一版用滚动数组的 `.length` 做判据，数组到 400 上限后不再变化，**误报「768 次里漏了 639 次」**；改成单调计数器后 2399 次绘制 0 次漏画，精灵层清白。
2. 拍了 14 张连拍截图 + 中心亮度统计，一张都没抓到——因为黑屏只持续一帧。**这种 bug 必须用像素探针，不能靠截图。**

修法是 deferred resize：`resize()` 只置脏标记 `_needResize`，`applyResize()` 在每帧 `update/render` 之前落地，保证「清空 → 重绘」发生在同一帧，且尺寸没变时直接早退。

### 4.3 GlowCache 按 (颜色, 半径) 做 key，400+ 张离屏 canvas

发光贴图按 `(颜色, 半径)` 缓存，而每个地形对象半径都不同 → 400+ 张离屏 canvas、几百 MB。移动端浏览器回收 GPU 显存后，表现同样是「发光没了 / 整屏没了」。

改成只按**颜色**做 key：

```js
const GlowCache = {
  map: new Map(),
  _make(color, R) { /* 预渲染一张 R 半径的径向渐变贴图 */ },
  get(color) {           // ← 只按颜色，绘制时用 drawImage 缩放
    let cv = this.map.get(color);
    if (!cv) { cv = this._make(color, GLOW_TEX_R); this.map.set(color, cv); }
    return cv;
  },
  small(color) { /* 弹幕用的 96×96 小贴图 */ },
};
```

验收断言 `GlowCache.map.size <= 24`，实测 6~11 张。

### 4.4 `'ontouchstart' in window` 在桌面 Chrome 上是 `true`

`detectPerf()` 原来用 `'ontouchstart' in window || navigator.maxTouchPoints > 0`。实测桌面 1440×810 无仿真：

```
ontouchstart: false, maxTouchPoints: 10, pointerCoarse: false → 但被判成 mobile=true
```

结果桌面被当成手机：DPR 降档、手机 HUD、缩放、小地图跑到左上角。

正确信号是 `matchMedia('(pointer: coarse)')`——它描述的是**主指针**，再配合 `min(innerWidth, innerHeight) < 820`。

### 4.5 头身分家：2° 的旋转能错开十几像素

角色头绕脖子转、身体绕脚底转，肩膀处杠杆约 190px，2° 就能让头和身体错开十几个像素。用户截图投诉「头身体分家了」。

修法不是调参数，是改结构：**把头部绘制挪进身体的 `ctx` 变换内部**，当头骨骼（子节点）→ 天然继承身体旋转。`ctx.save()` 嵌套顺序必须是 腿 → 身体 → 头。

顺带记一条方法论：**别用「和原图逐位比对」判断分层对不对**，必须先跑一个纯 WebP 往返的误差基线。

| 方向 | 分层合成误差 | 纯 WebP q92 往返误差 |
| --- | --- | --- |
| front | 5.73 | 5.71 |
| side | 4.99 | 5.03 |
| back | 3.94 | 3.97 |

两组几乎相同 → 分层重建是无损的，差异全来自有损压缩。没有基线的话，我会把压缩误差当成自己的 bug 追一整天。

最终效果：上排是走路四个相位，下排是睁眼 / 半闭 / 全闭。

### 4.6 闭眼帧：AI 生成整图 + 局部贴回

程序化眨眼失败后，改成「AI 生成闭眼整图，再只把眼皮区域贴回去」。又踩了一串对齐坑：

- `Image.getbbox()` 按 `alpha > 0` 会把边缘**半透明光晕**算进包围盒，缩放基准偏 20+ 像素。必须自己写 `solid_bbox(im, thr=200)`。
- 图已经裁到包围盒了，贴回坐标就是 `(rb[0], rb[1])`，**不能再减一次偏移**——我第一版就是错的，偏了 74px、交并比只有 0.48。
- 对齐要**按纵向**做（头顶/脚底最可靠），横向 AI 会把头发尾巴画更宽。
- 匹配用的「环带」要够大：整脸大框减去两只眼（6500~10000px），且要同时满足原图和生成图都**不透明**，否则透明像素被当黑色拉偏。

修完交并比 0.987，贴片外像素与原图逐位相同 → 眨眼不抖。

### 4.7 打包把 AI 原画打进去了，首屏 15.6 秒

`build_dist.py` 的 `ASSET_DIRS = ['heroes']` 是整目录 walk、没有后缀过滤，把 8 张 AI 原画 `.png`（约 2MB）打进了 `dist/`，而代码只引用 `.webp`。

加上 `ASSET_DIR_EXTS = ('.webp',)` 后：**3.8MB / 51 文件 → 2.0MB / 43 文件**。

另一个更隐蔽的教训：修完体积后线上仍是首次 11.7s、第二次 0.7s——那是**托管沙箱冷启动**，不是包体积。判断「线上慢」必须先做这个区分。

### 4.8 兜底越堆越多，最后堆出一整屏生命周期处理

为了治安卓 WebView / 微信内置浏览器后台丢弃 canvas 后备存储导致的黑屏，`main.js` 最终堆了：`dt > 1s` 判后台返回、`visibilitychange` 自动暂停并重建、`pageshow`（bfcache）、`orientationchange` 延迟补帧、3s 定时器检测主循环卡死，以及用 `getImageData(2,2,1,1)` 查 alpha=0 的画布健康自检——因为 `getImageData` 在某些安卓机上要十几毫秒，还得做成自适应周期（单次 > 8ms 就翻倍，上限 30s），免得自检本身造成掉帧。

其中最有用的一层是**单帧出错不锁死**：`render()` 抛异常时画一层安全底色 + 顶部红条，玩家能看到堆栈，我也能拿到线索。

## 5. 使用反思：AI 帮了我什么，又把我带偏到哪

这一节是全文最重要的部分。前面那些坑，本质都是「工程细节」，花时间总能修；下面这些才是我想写给别人的东西。

### 5.1 我承认：它不好玩

先把话说清楚。这个游戏：

- **能跑**，能上线，手机横竖屏都能玩，68 项自动验收全过
- **有内容**：4 角色、6 关、20 技能、6 地形、3 阶段 BOSS、局外成长
- **看起来挺像回事**

但它**不好玩**。

而且这跟引擎无关、跟代码量无关、跟画面无关。整个项目零依赖、没有引擎、就是一张 canvas + 9 个 script，纯前端完全够把这个玩法做出来。问题是：**「能实现」和「值得玩」是两件事**，我把全部精力花在了前者上。

### 5.2 决策密度接近零

玩家实际要做的事只有一件：**走位**。

攻击自动锁定最近敌人、自动开火，token 自动吸附，升级自动弹窗。手机端更极端——自动模式下全屏任意落指就是移动摇杆，一根拇指完成全部操作。

唯一的「选择」是升级三选一。但看 `config.js` 里的 20 个技能，绝大多数长这样：

```js
{ id: 'prompt',      apply: p => { p.atkMul *= 1.18; },        // 伤害 +18%
{ id: 'temperature', apply: p => { p.aspdMul *= 1.15; },       // 攻速 +15%
{ id: 'parallel',    apply: p => { p.countAdd += 1; },         // +1 投射物
{ id: 'context',     apply: p => { p.rangeMul *= 1.22; },      // 射程 +22%
```

它们是**同一个乘区的不同系数**：没有互斥、没有前置、没有代价、没有协同、没有「这局走穿透流还是召唤流」的分叉。抽卡逻辑还给「没拿过的技能」2 倍权重，理由是「让流派成型更快」，实际效果是**鼓励平均点**，把本就稀薄的选择进一步抹平。

「采样温度」三档是唯一需要主动按的按钮，但它也是全局乘区切换，不构成局面判断：不存在「现在该切低温」的时机，只有「我偏好哪个」。

对照同类游戏为什么耐玩：靠的是**构筑取舍**（选 A 就放弃 B）、**时机决策**（何时进危险区换资源）、**随机构筑之间的化学反应**。这三条我一条都没有。

**「20 个技能」听起来丰富，实际只是 20 个乘数字。**

### 5.3 难度是「数量」，不是「结构」

```js
spawnRate = CFG.SPAWN_BASE + this.time * CFG.SPAWN_GROW;   // 线性增长
```

敌人按时间表解锁（45/100/170/240/320 秒），六个关卡的差别只是倍率。敌人行为分了追击 / 冲刺 / 弹幕，但威胁模型单一：**更多的血、更快的速度、更密的弹幕**。

结果是玩家的解法从头到尾不变：绕圈、别被贴脸、把数值叠上去。

`MAX_ENEMIES: 420` 和弹幕上限是**性能上限，不是设计上限**；「无限推理」关就是没有阶段、怪越来越多，没有新规则、没有组合威胁、没有需要改变打法的节点。BOSS 三阶段 8 种弹幕是全场最像设计的部分，但它前面是 55~80 秒几乎无变化的清怪。

### 5.4 反馈层太薄

视觉风格做得很足：CRT 扫描线、数据雨、glitch 标题、注意力热力斑块、潜空间晶格连线、世界分区环、溢出红色暗角。击杀有粒子和浮动伤害字，暴击字放大 1.5 倍带发光，相机有 shake。

但**声音只有几声程序化方波和噪声**——没有音乐、没有节奏起伏、没有「危险临近」的听觉预警、没有击杀手感的层次差异。受击、击杀、升级、BOSS 登场的区别只是振荡器频率不同。

视觉上「很满」，体感上「很平」：**风格是包装，不是玩法反馈。**

### 5.5 数值根本没被验证过

唯一一次平衡对照：同一套走位 bot 各跑 2 局 120 秒。

| 组 | 结果 |
| --- | --- |
| A（新机制开启） | 57s 死 / 104s 活，平均 81s、539 击杀 |
| B（关掉部分机制） | 107s 活 / 34s 死，平均 71s、443 击杀 |

**方差极大，单局结果不能当结论；而且方向还是反的——新机制没让游戏变难，反而略轻松。**

为什么？因为我给玩家 +55% 伤害 +15% 暴击，只给敌人 +30% 移速 +22% 伤害。「风险机制」变成了纯奖励。

日志里我自己写了「方差很大，单局结果不能当结论」，然后就没有然后了——没有留存、没有单局时长分布、没有重开率、没有真人试玩记录。

**一个没有数值验证的割草游戏，剩下的只能是「能跑通」。**

### 5.6 元进度与目标错位

打通一关 → 点「下一关」；死亡 → 结算 → 拿算力币 → 买 10 项永久数值加成 → 再来一局。

没有叙事、没有成就、没有里程碑、没有「这一局我要试试某种构筑」的理由。局外升级把失败解释成「再刷几局就变强」，而不是「再想一次怎么打」，反而进一步削弱局内决策的重要性。

而且这套元进度是**后加的**：`meta.js` 里还留着「角色尚未实装，配置先留档」的注释。它是功能清单上的一项，不是从玩法里长出来的需求。

### 5.7 那我到底用 AI 换到了什么

**换到的，非常实在：**

1. **把想法压缩到「当天能点开的链接」**。没有 AI，一个人不会在同一个下午里同时做骨骼切件、移动端适配、PWA、平台包体积预检。
2. **声明式数据的填充能力**。给它一个 `STAGES` 的结构，它能一口气填满六个关卡、二十个技能，还顺手写出带条件的 `desc(lv)`。
3. **可验证的小工具写得极好**。那 24 个 CDP 脚本（设备仿真、像素探针、对比断言、实战 bot）质量相当高，比我手写快一个数量级。
4. **调查与方案**。平台规格、资质时间线、包体积量化，AI 一次能给出结构完整的调研文档——当然数字要自己核。

**付出的，更结构性：**

1. **生成成本太低，用「加功能」代替「设计玩法」。** 「再加一个机制」比「想清楚现有机机制为什么不好玩」容易一百倍，于是项目一路膨胀成功能清单。6 种地形、20 个技能、3 阶段 BOSS 都是几天内堆出来的，但没有一样逼我回答那个真正的问题：**玩家在这一秒，究竟在犹豫什么？**
2. **AI 擅长局部正确性，不擅长跨系统的手感。** 一个 `SkillSystem.roll()` 写得无误，但「20 个乘区会不会让选择变无意义」没有局部判据可依。
3. **AI 不会替你玩 100 局。** 数值、节奏、难度曲线需要有人反复试、有数据。这一步被跳过了。
4. **排查类问题必须先由人定义判据。** 一帧黑屏、假测试、压缩误差基线——AI 能写探针，但「什么算通过」得人先想明白。
5. **半成品会被包装得非常完整。** 这个项目里最刺眼的例子：`dist-tt/` 有 27 张量化 PNG、`game.json`、`project.config.json`，`build_tt.py --check` 还会打印「1.45MB / 4MB，无需分包」，看着像移植快做完了——**但 `dist-tt/game.js` 全文只有 4 行**：

```js
/* 抖音小游戏入口 —— 占位。
   移植时替换为：require('./js/platform/platform.tt.js') 并启动主循环。 */
console.log('[TOKEN幸存者] 抖音入口待接入');
```

6. **素材合规、授权、平台类目这些「非代码问题」，AI 不会主动提醒。** 主角色形象源自社区二创（CC BY-NC-SA 4.0，禁商用），技术 demo 无所谓，一旦谈上线变现就是硬阻塞；AI 模型拟人命名还带来平台类目与商标风险。

一条可以直接拿走的工作方式：

> **让 AI 写实现，人负责判据、优先级，以及最难的那一件事——砍功能。**

### 5.8 三种「假成功」信号，我全中过

复盘时我把「让我误以为它快成了」的信号单独列了出来，因为它们比 bug 更危险：

| 信号 | 我看到的 | 实际情况 |
| --- | --- | --- |
| **验收全绿** | 手机横竖屏 68 项断言全过、算力币 90/90 | 断言只覆盖「能不能用」，不覆盖「好不好玩」 |
| **功能清单长** | 20 技能、6 地形、6 关卡、3 阶段 BOSS | 每一个都是乘数/倍率，决策密度没变 |
| **产物很像成品** | `dist-tt/` 有量化 PNG、`game.json`、体积报告 | 入口 `game.js` 是 4 行占位 |

第三条尤其值得警惕：**外围越完整，越容易让人（包括我自己）以为已经做完。** AI 很擅长把「外围」铺满——配置文件、构建脚本、验收报告、上线方案文档——这些都是它的舒适区，而核心那一行「启动主循环」反而没人写。

### 5.9 一个反直觉的观察：AI 让「技术债」和「设计债」同时膨胀，但只有前者会疼

回头看，我在工程上其实踩对了几个关键点：

- **逻辑与表现分离**：核心逻辑（配置/实体/地形/技能/战斗）约 3400 行**零 DOM 依赖**，后来评估抖音移植时，这部分一行都不用改。
- **`Storage` 抽象层**：一开始只是为了包 `localStorage`，后来成了唯一能直接复用到小游戏平台的部分。
- **数据驱动**：`config.js` 集中数值，改平衡不用翻代码。

但设计上几乎每一步都错：技能全是乘区、难度全是倍率、反馈只有视觉。

为什么？因为**技术债会立刻报错，设计债不会**。技术债报错时，AI 十分钟给你一个修法；设计债报错时，它只会安静地把游戏变成一个「能跑的空壳」。

---

## 6. 将来做游戏，我会按这个顺序来

这一节是我真正想留下的东西。假设明天再从零做一款游戏，我会换成下面这套流程。

### 6.1 先写「一句话决策」，再写第一行代码

在打开编辑器之前，先逼自己回答三个问题，写在 README 第一屏：

1. **玩家每 3 秒要做一次什么判断？**（不是「移动」，是「往左躲还是往右贪一个 token」）
2. **这个判断的两种答案，代价分别是什么？**（左边安全但少拿 3 个 token；右边贪到但掉 20 血）
3. **同一局里，这个判断会变几次？**（10 次以内说明深度不够）

如果三个问题答不上来，说明现在做的不是游戏，是**交互式演示**。演示可以做完，但别指望它好玩。

### 6.2 用「灰盒原型」先验证决策，再谈美术

我这次是反过来做的：先有精美立绘和终端风视觉，再往上加玩法。

正确顺序应该是：

| 阶段 | 用什么 | 验证什么 | 时间预算 |
| --- | --- | --- | --- |
| 灰盒 | 纯色方块 + 文字 | 决策是否成立、节奏是否成立 | 1~2 天 |
| 手感 | 加粒子、抖动、音效、命中停顿 | 操作是否有反馈快感 | 1~2 天 |
| 内容 | 加技能、敌人、关卡 | 组合是否有变化 | 视规模 |
| 包装 | 立绘、UI、风格化 | 是否让人愿意点开 | 最后 |

**关键：灰盒阶段就应该能玩得下去。** 如果方块对撞就不好玩，加上立绘只会变成「好看的不好玩」。

### 6.3 技能设计：从「乘区」换成「互斥流派」

这是我最想改的一条。现在 20 个技能是 20 个乘数，应该改成 **8 个技能、3 条互斥流派**：

```
穿透流（长线贯穿，打密集直线）  ─┐
召唤流（Agent 协战，越打越多）   ─┼─ 选了就锁死另外两系
溢出流（主动踩溢出，高风险高回报）┘
```

配套的判据：

- 每条流派有 2~3 个**只有本流派能拿到**的核心技能
- 流派之间要有**互相克制**的敌人（例：穿透流怕分散的快速单位，召唤流怕清场 AOE）
- 升级三选一里，至少有一张是「跨流派但代价明显」的诱惑牌

这样「三选一」才真的是「这局往哪走」，而不是「再乘 1.18」。

### 6.4 难度设计：从「倍率」换成「组合威胁」

不要用「45 秒解锁血更厚的怪」这种方式加难度，改成**威胁组合**：

| 阶段 | 威胁组合 | 逼玩家做什么 |
| --- | --- | --- |
| 前 60s | 只追击 | 学走位 |
| 60~120s | 追击 + 远程压制 | 学会绕掩体 |
| 120~180s | 追击 + 远程 + 减速场 | 学会取舍站位 |
| BOSS 前 | 上面三种同时 + 自爆 | 被迫用主动技能 |

判断标准是：**每次加新威胁，玩家必须改变一次打法**。如果只是「更疼一点」，那不算新内容。

### 6.5 数值验证：先定目标，再跑统计

这次我最大的失误是把「跑了两局 bot」当成了平衡验证。正确做法：

1. **先写目标**：单局 8 分钟、升级选择熵 > 0.8、不同流派胜率差 < 10%
2. **固定种子跑 30 局起步**，看**分位数**而不是平均值（p10 / p50 / p90）
3. **每次改动跑同一套种子**，否则比的是随机数不是改动
4. **真人试玩 ≥ 5 人**，只看两件事：第一次死亡的时间点、重开前犹豫了多久

第 4 条 AI 永远替不了你。

### 6.6 反馈分层：声音不是装饰，是信息

这次「零音频文件」看着很酷，实际是灾难。下次至少要有四层：

| 层 | 作用 | 最低要求 |
| --- | --- | --- |
| 音乐 | 铺底、节奏提示 | 一段可循环的 loop，或干脆不要 |
| 危险预警 | 告诉玩家「该躲了」 | BOSS 蓄力 / 弹幕生成前 0.3s 的短音 |
| 命中反馈 | 告诉玩家「打中了」 | 命中 / 暴击 / 击杀三种不同音色 |
| UI 音 | 告诉玩家「操作生效了」 | 升级、拾取、按钮 |

配合视觉：**命中停顿**（hitstop 30~50ms）、**受击方向闪白**、**击杀时的一帧放大**。这些比多加十种粒子有效得多。

### 6.7 架构：这次做对的和做错的，都要固化下来

**做对的，继续用：**

- 逻辑与表现分离（核心逻辑零 DOM）→ 这次让「移植评估」变成「换壳而非重写」
- 数据驱动（`config.js` 单一数值真相）→ 改平衡不动逻辑
- 平台抽象层（`Storage`）→ 一开始只包 `localStorage`，后来直接复用

**做错的，下次改：**

- **UI 全压在 DOM 上**：`ui.js` 835 行里有 **120+ 处 DOM 调用**，加上 1342 行 CSS 整体作废。多端发布的前提是「UI 也能画在 canvas 里」，这不是优化项，是架构项。
- **裸全局 + 加载顺序**：为了 `file://` 双击可跑值得，但应该在第三天就切到 ES Module + Vite，而不是留到最后。
- **无对象池、O(n²) 碰撞**：靠 `MAX_ENEMIES` 硬压。手写没问题，但至少上网格空间索引。
- **无类型**：数值表这么多，TypeScript 的 `as const` 能挡掉一半「字段名写错」的低级错误（我就写过 `p.pspdMul`，实际字段叫 `p.pspd`）。

### 6.8 AI 的正确用法：把它当「执行团队」，不当「制作人」

具体到协作方式，我会这样分工：

| 谁 | 负责 |
| --- | --- |
| **人** | 玩法核心循环、判据定义、数值目标、砍功能、真人试玩 |
| **AI** | 实现、重构、写验证脚本、写文档、批量填数据、查 API |
| **人 + AI** | 排查（人定判据，AI 写探针）、调研（AI 出结构，人核数字） |

三条硬规则：

1. **每个功能进代码前，先回答「它让玩家多做什么判断」**。答不上来就不做。
2. **AI 生成的东西必须过一个「可验证的判据」**。不能验证的东西（比如「好不好玩」）不要交给 AI 下结论。
3. **每周留一天不加功能**，只玩自己做的游戏，并且记录「我在哪一秒觉得无聊」。

第 3 条是我这次最缺的。

### 6.9 发布与合规：这些不是代码问题，但会先杀死你

- **素材授权**：AI 生成 + 社区二创混用，商用前必须逐张确认。CC BY-NC-SA 意味着禁商用 + 必须署名 + 相同方式共享。
- **平台类目**：AI 模型拟人角色在部分平台容易被判「角色类」，个人主体不能选。要么改类目论证（强调「单局制割草生存」），要么注册个体户。
- **软著 / 备案**：60 天量级，与开发完全并行，**第一天就该提交**。
- **固定域名**：临时预览通道每次发布可能换域名，正式发要提前准备静态托管。

## 7. 结论

我做出了一款「技术上成立、产品上不成立」的游戏。

**技术上成立的部分：**

- 浏览器 + Canvas 2D + WebAudio + localStorage 足够实现割草玩法，**不需要引擎**
- 7360 行零依赖代码，`file://` 双击可跑，`dist/` 2.12 MB
- 手机横竖屏 68 项自动验收全过，一帧黑屏这类最难查的 bug 也被像素探针定位并修掉

**产品上不成立的部分：**

- 能跑 ≠ 好玩，功能多 ≠ 决策多
- 20 个技能只是 20 个乘数字；6 个关卡只是 6 组倍率
- 数值从未被验证，声音几乎不存在，元进度是后加的

**最大的收获不是这个游戏，是这条教训：**

> AI 把「加一个功能」的成本压到接近零，于是我用「不断加功能」代替了「设计玩法」。它让技术债变得便宜，同时让设计债变得隐形——而隐形的那种债，最后是用「不好玩」来还的。

**下一步我不会再加功能了。** 要么按 6.3~6.6 把技能砍到 8 个、重做决策与数值验证；要么干脆把它归档成技术 demo，写在标题里，别当产品运营。

做技术验证，它已经合格了。
