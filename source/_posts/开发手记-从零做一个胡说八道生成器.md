# 我用 1058 行 HTML 做了个「知识搅拌机」：一个一本正经胡说八道的生成器

> 不需要懂框架、不需要懂构建工具、不需要会配环境。
> 如果你能看懂 `<div>` 和 `if`，这篇你就能看完。

## 一、先说这东西是干嘛的

打开它，你会看到一个聊天窗口。你点「搅 一 搅」，它就开始往外吐话：

> 「意大利面应该拌42号混凝土，这一点没什么可商量的。」
>
> 「因为二创的重量会直接决定晾衣架的机会成本，所以羞耻感必须赎回退货。」
>
> 「从置顶的角度看，下沉市场催眠秋裤是必然的。」

每一句**语法完全正确**，用词**一本正经**，逻辑链条**看起来严丝合缝**，但把每个词单独拎出来都认识，连起来就是浑然天成的废话。

它还有几个开关：

- **场景**：随便 / 应付亲戚 / 跟老板汇报 / 相亲现场 / 群聊炸场 / 学术答辩
- **模式**：对话 / 单句 / 长文 / 接话
- **浓度**：轻 / 中 / 重
- **关键词注入**：你想让某些词出现，塞进去，它一定会用上
- **发疯指数**：给每次生成打个分
- **存图**：导出一张聊天记录截图发朋友圈

整个东西**一个 HTML 文件，1058 行，零依赖，零后端**。双击就能开，发微信里也能开。

这个「零」，是我后面所有技术选择的总纲。下面按顺序讲：为什么这么定、词库怎么分的、句子怎么拼的、以及几个踩过的坑。

## 二、第一个决定：不要 AI

看到「生成器」，第一反应肯定是接个大模型 API。我一开始也想过，但很快否掉了。

**原因一：慢。** 调一次 API 少说一秒多，网络不好的时候三五秒。而这个产品的爽点是「点一下立刻出结果」。你要的是瞬间的荒谬感，不是等待。

**原因二：贵。** 这是个玩具。为了让人点十次，付十次 token 钱，不划算。

**原因三，也是最重要的——AI 写不出这种味道。**

大模型天然会「圆回来」。你让它说胡话，它说着说着就开始自洽、开始有主题、开始像一个认真的解释。它会有内在一致性，而**荒诞恰恰来自不一致**。

我要的效果是：前半句教你做人，后半句用螺丝刀撬开宇宙。这种「完全不搭但语法通畅」的组合，反而是**随机**最擅长的——只要我给它的原料足够刁钻。

所以最终方案是：**模板 + 随机填词**。一句话的骨架由我手写，血肉由词库随机组合。

这带来一个额外的好处：**完全离线，打开就能用，不联网也不花钱。**

## 三、核心思路：荒诞 = 语法正确 × 语义距离

这是整个项目唯一一个「设计理论」，想通了这一句，后面全是体力活。

一句话好笑，不是因为词奇怪，是因为**两个词在现实里永远不会出现在同一个句子里，但它们的语法位置完全合法**。

举例：

> 「如果**屁股**能够**放生****面包**，也许**海鸥**也能够**生产****交通工具**。」

拆开看：

| 位置 | 填的词 | 来自哪个域 |
|---|---|---|
| 主语 A | 屁股 | 身体 |
| 谓语 V | 放生 | 动词库 |
| 宾语 B | 面包 | 食物 |
| 主语 C | 海鸥 | 动物 |
| 谓语 V | 生产 | 动词库 |
| 宾语 D | 交通工具 | 交通工具 |

**语法骨架完全正确**：「如果 A 能够 V B，也许 C 也能够 V D」是个标准条件句。

**语义上**：屁股（身体）× 放生（宗教/慈善）× 面包（食物），三个域的语义距离被拉到最远。海鸥（动物）× 生产（工业）× 交通工具（交通），同样是三个不搭界的东西。

于是荒诞感就出来了，而且它是「一本正经」的荒诞——因为句子本身没问题。

### 从这句话推导出两个设计要求

1. **词库必须按「语义域」分桶，不能是一锅乱炖。**
   如果我把所有词塞进一个数组随手抽，抽到「屁股」和「脚趾甲」的概率一样高，两个都是身体部位，语义距离太近，不荒诞。必须**先选域，再选词**，并且尽量让同一句里的词来自不同的域。

2. **句模必须是「正经句式」，不能是「搞笑句式」。**
   如果模板写的是「我跟你讲，A 居然 V 了 B，笑死」，那它从第一秒就在告诉你「我要搞笑了」。正经句式（学术论证、长辈训话、老板画饼）才能让荒谬词被包装成严肃论述，反差才成立。

这两条决定了后面所有数据结构的样子。

## 四、数据结构：五个词库 + 一个句模表

对着代码讲。整个项目的数据就六样东西，全在 `<script>` 开头。

**为什么是这 19 个域？** 因为它们互相之间**几乎不可能共现**。你不会在一句话里同时讨论「扁桃体」和「关税」，也不会把「螺蛳粉」和「举证责任」放在一起。域和域之间的距离，就是荒诞感的来源。

**为什么每个域 20~30 个词？**
- 太少了（比如 5 个），同一个词重复出现，新鲜感三下就没。
- 太多了，我得手工保证每个词都不重复、都有效，维护成本爆炸。
- 20~30 是个甜点：19 个域 × 平均 24 个词 ≈ 460 个词，手动管理还吃得消，组合出来的量已经用不完。

选词也有讲究。**不要选「抽象大词」，要选「具体到有画面感的名词」**。比如「膝盖」比「身体」好，「螺蛳粉」比「食物」好，「马桶搋子」比「工具」好。画面感越强，荒谬感越具体。

### 4.2 语气分级 `TONE`

有些词是「俗的」（屁股、螺蛳粉、秋裤），有些是「专业的」（承重墙、显卡驱动、民法典），有些居中。

```js
const TONE = {
  body:"vulgar", food:"vulgar", animal:"vulgar", clothes:"vulgar",
  ritual:"vulgar", tool:"vulgar",
  build:"pro", tech:"pro", bio:"pro", chem:"pro", social:"pro", law:"pro",
  vehicle:"mid", space:"mid", culture:"mid", sport:"mid",
  emotion:"mid", agri:"mid", media:"mid"
};
const TONE_VAL = { vulgar:0, mid:1, pro:2 };
```

这个分级有两个用途，后面都会用到：

1. **控制句子的「混搭」风格**。每个句模带一个 `mix` 属性（`"vp"` / `"vulgar"` / `"pro"` / `"any"`），决定这句里的实体从什么语气的域里抽。`"vp"` 是交替抽：第一个位置抽俗的，第二个抽专业的，造成**剧烈反差**。
2. **算「发疯指数」**。一句里同时出现最俗和最专业的词，跨度最大，分最高。

`TONE_VAL` 把语气映射成 0/1/2，就是为了能算「跨度」这个数值。

### 4.3 非实体词库

除了名词，句子里还需要谓语、修饰、吐槽用的「大词」。这些不按语义域分，按**词性功能**分：

```js

const VT = ["放生","生产","腌制","焊接","抛光","接种","抵押","编译","发酵",

// 变化动词（不及物）：表示「崩坏」的结果
const VI = ["失效","坍缩","氧化","脱臼","结痂","结晶","断供","过户","漏电",

// 伪专业术语：让句子显得「有指标」
const TERM = ["扭矩","阻尼系数","屈服强度","渗透率","击穿电压","热导率",

```

`VT` 和 `VI` 分开，是因为它们**语法功能不同**：
- `VT` 是他动词，后面要跟宾语：「放生面包」「焊接情绪阈值」
- `VI` 是不及物动词，表示状态崩坏：「彻底坍缩了」「开始氧化」

分开了，句模才能写得通顺。这是「语法正确」这条铁律在数据结构上的体现——**连动词都要按能不能带宾语分类**。

### 4.4 句模表 `TPL`

这是项目的灵魂。32 条句子骨架，按「浓度」分三级。

```js
const TPL = [
  { level:1, mix:"vp",  t:"如果{A}能够{V}{B}，也许{C}也能够{V}{D}。" },
  { level:1, mix:"any", t:"既然{A}可以{V}{B}，{C}就没有理由不能{V}{D}。" },
  { level:1, mix:"any", t:"难道你们都没发现，{A}其实一直在{V}{B}吗？" },
  { level:1, mix:"any", t:"{A}的{P}，本质上是被{C}的{F}决定的。" },
  { level:1, mix:"any", t:"{A}的{F}一旦超过{P2}，{B}就会{V3}。" },

  { level:2, mix:"any", t:"{A}之所以{V}{B}，是因为{C}的{P}直接影响了{D}的{F}。" },
  { level:2, mix:"any", t:"长期来看，{A}的{P}会直接拖垮{C}的{G}。" },
  { level:2, mix:"any", t:"从{C}的角度看，{A}{V}{B}是必然的。" },

  { level:3, mix:"vp",  t:"我不敢苟同，{A}不但应该{V}{B}，还必须同时{V2}{C}，否则{D}的{F}根本稳不住。" },
  { level:3, mix:"any", t:"你只看到了{A}在{V}{B}，却没看到{C}的{P}已经悄悄改变了{D}的{F}，这才是最要命的地方。" },
  { level:3, mix:"any", t:"如果把{A}、{B}和{C}放在同一个框架里看，你会发现它们其实共享同一套{G}，只不过表现形态不同。" }
];
```

**槽位标记**就是 `{A}` `{B}` `{V}` 这种花括号，生成时用正则替换。

槽位对照表：

| 占位符 | 含义 | 从哪抽 |
|---|---|---|
| `{A}` `{B}` `{C}` `{D}` `{E}` | 实体名词 | `LEX`，按 `mix` 规则选域 |
| `{V}` `{V2}` | 他动词 | `VT` |
| `{V3}` `{V4}` | 不及物动词 | `VI` |
| `{P}` | 属性 | `PROP` |
| `{P2}` | 阈值 | `LEVEL` |
| `{F}` | 伪专业术语 | `TERM` |
| `{G}` | 抽象大词 | `ABS` |
| `{H}` | 灾害词 | `HARM` |
| `{T}` | 理论名 | `THEORY` |
| `{L}` | 地点 | `PLACES` |
| `{U}` | 用户原话（只在接话模式） | 输入框 |

**浓度三级的区别**不是「越多越黄」，而是**句子的复杂度**：

- **level 1（16 条）**：单层因果。「A 应该 V B，没什么可商量的。」
- **level 2（12 条）**：双层因果，开始引用属性。「A 之所以 V B，是因为 C 的 P 影响了 D 的 F。」
- **level 3（4 条）**：三层嵌套 + 术语轰炸 + 转折。「我不敢苟同，A 不但应该 V B，还必须同时 V2 C，否则 D 的 F 根本稳不住。」

为什么 level 3 只有 4 条？因为**写长句很难**。每多一个槽位，语法出错、重复、不通顺的概率都在涨。我写了二十几条，最后能用的就这 4 条。宁可少，不能烂。

顺便说个数据：32 条模板，平均 3 个实体槽、2 个其他槽。理论上单条模板的组合数是 `C(19,3) × 24³ × 51² × ...`，量级是**十的十几次方**。也就是说，实际使用中你几乎不可能看到重复的句子。

## 五、核心引擎：三个函数

整个生成逻辑就三个函数：`render`（填词）、`pickEntity`（选词）、`pickTpl`（选模板）。

### 5.1 `render`：把 `{A}` 换成真词

```js
const genCtx = { pool: [], usedInSentence: 0, cap: 3 };

function render(tpl, opt) {
  opt = opt || {};
  const used = new Set();     // 本句已经用过的语义域，避免重复
  const memo = {};            // 同一个占位符只填一次
  let entIdx = 0;             // 第几个实体槽，用于 vp 交替
  genCtx.usedInSentence = 0;

  return tpl.replace(/\{([A-Z]\d?)\}/g, function(m, key){
    // 关键：同一个 key 出现两次，用同一个词
    if (Object.prototype.hasOwnProperty.call(memo, key)) return memo[key];

    let val;
    switch (key) {
      case "A": case "B": case "C": case "D": case "E": {
        let tone = "any";
        if (opt.mix === "vp")       tone = (entIdx % 2 === 0) ? "vulgar" : "pro";
        else if (opt.mix === "vulgar") tone = "vulgar";
        else if (opt.mix === "pro")    tone = "pro";
        entIdx++;
        val = pickEntity(tone, used);
        break;
      }
      case "V": case "V2": val = pick(VT); break;
      case "V3": case "V4": val = pick(VI); break;
      case "P":  val = pick(PROP);   break;
      case "P2": val = pick(LEVEL);  break;
      case "F":  val = pick(TERM);   break;
      case "G":  val = pick(ABS);    break;
      case "H":  val = pick(HARM);   break;
      case "T":  val = pick(THEORY); break;
      case "L":  val = pick(PLACES); break;
      default:   return m;   // 不认识的占位符，原样保留
    }
    memo[key] = val;
    return val;
  });
}
```

这里有两个**必须**做对的地方，都是踩过坑之后加的：

**坑一：同一个占位符必须填同一个词。**

如果模板是「{A}和{B}之间是有严格对应关系的」，渲染时如果不去重，可能出现「屁股和屁股之间」——直接毁掉整句话。

所以用 `memo` 对象缓存：`{A}` 第一次抽到「屁股」，第二次再遇到 `{A}` 就直接复用。这一步不做，一半的句子会变成复读机。

**坑二：同一句里尽量不用同一个语义域。**

如果 `{A}` 抽到「屁股」（身体域），`{B}` 又抽到「膝盖」（还是身体域），语义距离就没了，句子不荒诞，只是莫名其妙。

所以 `pickEntity` 里有个 `used` 集合：

```js
function pickEntity(tone, used){
  // 1. 关键词优先：用户塞的词，一定要用上
  if (genCtx.pool.length && genCtx.usedInSentence < genCtx.cap) {
    genCtx.usedInSentence++;
    return genCtx.pool.shift();
  }
  // 2. 按语气过滤 + 排除本句已用过的域
  let pool = DOMAINS.filter(function(d){
    return (tone === "any" || TONE[d] === tone) && !used.has(d);
  });
  // 3. 兜底：语气匹不上就只排除已用域
  if (!pool.length) pool = DOMAINS.filter(function(d){ return !used.has(d); });
  // 4. 再兜底：实在没得选，全部放开
  if (!pool.length) pool = DOMAINS;

  const d = pick(pool);
  used.add(d);
  return pick(LEX[d]);
}
```

这三层 `if` 是**逐级降级**的思路，很重要：

- 第一层：既要语气对，又要没用过——最理想
- 第二层：语气顾不上了，但至少别重复域
- 第三层：都顾不上了，随便抽，总比报错强

写代码的时候很容易只写第一层，然后某个语气词库小的时候直接抽空数组，报 `undefined`。**兜底不是「过度设计」，是让随机函数能一直跑下去的必需品。**

### 5.2 关键词注入：让用户感觉「我说了算」

输入框里塞的词，最终都要出现在句子里。这里的逻辑在 `pickEntity` 的前两行：

```js
if (genCtx.pool.length && genCtx.usedInSentence < genCtx.cap) {
  genCtx.usedInSentence++;
  return genCtx.pool.shift();
}
```

`pool` 是用户输入的词排成的队列，`shift()` 每次取一个，取完就没了。`cap` 是「一句最多塞几个」，防止一句话被你塞的词占满。

不同模式 `cap` 不一样：

| 模式 | `cap` | 原因 |
|---|---|---|
| 对话 | 1 | 一句塞 1 个，分散到多条消息，读起来自然 |
| 长文 | 2 | 篇幅长，可以塞得多 |
| 单句 | 3 | 只有一句，必须全塞进去 |

**但光有 `cap` 还不够。** 如果生成的是对话，有 5 条消息，你的词有 3 个，`cap=1`，那刚好用完。可如果生成的对话只有 3 条消息呢？词就用不完了。

所以 `generate()` 里有兜底：

```js
// 关键词没用完，兜底补一句，保证用户输入的词一定出现
if (genCtx.pool.length) {
  genCtx.usedInSentence = 0;
  const t = pickTpl(state.level);
  list.push({
    side: state.mode === "single" ? "left" : "right",
    text: render(t.t, { mix: t.mix })
  });
}
```

> **这是个产品层面的决定，不是技术层面的。**
> 用户塞了一个词，结果生成的话里没有——哪怕只发生一次，用户的信任就没了。
> 「我输入的东西一定会出现」这个承诺，比「句子质量高一点」重要得多。
> 所以我宁可偶尔多出半句略显冗余的话，也要保证这个词一定在。

### 5.3 `pickTpl`：选模板，别重复

```js
function pickTpl(level, used, minSlots) {
  let pool;
  if (level <= 1)      pool = TPL.filter(t => t.level === 1);
  else if (level === 2) pool = TPL.filter(t => t.level <= 2);
  else                 pool = TPL.filter(t => t.level >= 2);

  // 单句模式下，要装下用户塞的所有词，优先选槽位够多的模板
  if (minSlots) {
    const enough = pool.filter(t => slotCount(t.t) >= minSlots);
    if (enough.length) pool = enough;
  }
  // 本轮已经用过的模板，排除掉
  if (used) {
    const fresh = pool.filter(t => !used.has(t.t));
    if (fresh.length) pool = fresh;
  }
  const t = pick(pool);
  if (used) used.add(t.t);
  return t;
}
```

注意 `level === 2` 时抽的是 `level <= 2`，`level === 3` 时抽的是 `level >= 2`。这不是 bug，是**故意的重叠**：中浓度里也偶尔能出重口味的句子，重浓度里也能出简单的句子。全是同一个难度，读起来会很单调。

`minSlots` 那段是为「单句模式 + 关键词注入」准备的。用户塞了 3 个词，结果抽到一个只有 2 个实体槽的模板，第三个词就塞不进去了。所以先筛「槽位够多」的模板。

`slotCount` 的实现有个细节：

```js
/* 统计句模里有几个【不同的】实体槽位（{B} 出现两次只算一个） */
function slotCount(tpl) {
  const m = tpl.match(/\{[A-E]\}/g);
  return m ? new Set(m).size : 0;
}
```

用 `new Set()` 去重。因为「{A}和{B}之间」这种模板，`{B}` 只出现一次算一个槽；但如果模板里写了 `{B}…{B}`，第二次的 `{B}` 会被 `memo` 复用，**并不吃新的词**。所以槽位数要按「不同占位符的个数」算，不是「出现次数」。

这个细节不做，会误判模板容量，导致关键词塞不进去。

## 六、四种「玩法」其实是四个函数

同一条引擎，套不同的外壳，就是四种模式。

### 6.1 对话 `genChat`

输出一组交替的左右气泡。关键在**场景**：

```js
const SCENES = {
  any:     { name:"随便",     structure:"duo", openers:[...] },
  family:  { name:"应付亲戚", structure:"ask", openers:["你今年多大了啊","有对象了吗",...] },
  boss:    { name:"跟老板汇报", structure:"ask", openers:["这个季度的进展你同步一下",...] },
  date:    { name:"相亲现场", structure:"ask", openers:["你平时有什么爱好",...] },
  group:   { name:"群聊炸场", structure:"duo", openers:[...] },
  defense: { name:"学术答辩", structure:"ask", openers:["请简述一下你的研究方法",...] }
};
```

`structure` 只有两种：

- `"ask"`：对方问，我答。开场是一句真实的人话（「有对象了吗」），后面全是我一本正经的胡扯。**这种反差最好笑**——因为提问是真实的、生活里真的会被问到，而回答离谱到极点。
- `"duo"`：双方一起发疯。没有固定的问答关系，你一句我一句地疯。

```js
function genChat(level, sceneKey) {
  const sc = SCENES[sceneKey] || SCENES.any;
  const used = new Set();       // 本轮用过的模板
  const msgs = [];
  genCtx.cap = 1;               // 对话里每句只塞 1 个关键词

  if (sc.structure === "ask") {
    msgs.push({ side:"left", text: pick(sc.openers) });
    const n = 3 + rnd(2);       // 3 或 4 条回复
    for (let i = 0; i < n; i++) {
      const t = pickTpl(level, used);
      msgs.push({ side:"right", text: render(t.t, { mix: t.mix }) });
    }
  } else {
    msgs.push({ side:"left", text: pick(sc.openers) });
    for (let i = 0; i < 2; i++) { /* 两条 left */ }
    msgs.push({ side:"right", text: pick(RIGHT_LEADS) });
    const n = 2 + rnd(2);        // 2~3 条 right
    for (let i = 0; i < n; i++) { /* 若干条 right */ }
  }
  genCtx.cap = 3;               // 恢复全局默认
  return msgs;
}
```

`3 + rnd(2)` 就是「3 或 4」，`rnd` 是 `Math.floor(Math.random() * n)`。**消息条数随机**很重要——固定条数会显得机械，差一条就有自然感了。

另外注意 `RIGHT_LEADS`：

```js
const RIGHT_LEADS = ["我觉得","不是","我觉得吧","我说句实话","你有没有想过","这么一说","那按这个逻辑"];
```

这是「我」开口前的口癖。真实聊天里，没人会一上来就抛出完整论证，总会先「我觉得吧」一下。加了这个，代入感立刻强一个档次。

### 6.2 长文 `genEssay`

固定结构的小论文，越长越离谱：

```js
function genEssay(level) {
  const out = [];
  const used = new Set();
  genCtx.cap = 2;

  // 1. 开场立论
  out.push({ side:"left", text: pick(OPENERS) });
  // 2. 亮出观点
  out.push({ side:"left", text: render(pick(CLAIMS), { mix:"vp" }) });
  // 3. 论证主体（2 或 3 条）
  const causalN = level >= 3 ? 3 : 2;
  for (let i = 0; i < causalN; i++) {
    const t = pickTpl(level >= 3 ? 3 : 2, used);
    out.push({ side:"left", text: render(t.t, { mix: t.mix }) });
  }
  // 4. 扩大影响
  out.push({ side:"left", text: render("这会严重影响{A}，甚至对整个{B}以及{C}都会造成一定的{H}。", { mix:"any" }) });
  // 5. 引用理论（中/重浓度才有）
  if (level >= 2) {
    out.push({ side:"left", text: render("再者说，根据{T}，你很容易推断出{A}其实一直在{V}{B}。", { mix:"any" }) });
  }
  // 6. 下结论（重浓度才有）
  if (level >= 3) {
    out.push({ side:"left", text: render("所以我的结论很明确：{A}必须{V}{B}，否则{C}的{G}迟早会{V3}。", { mix:"vp" }) });
  }
  genCtx.cap = 3;
  return out;
}
```

这个结构是照着**真实议论文**抄的：**立论 → 观点 → 论证 → 影响 → 引据 → 结论**。

荒诞感不来自结构，结构必须是正经的；荒诞感来自**每一层里填的词**。这就是「一本正经」的机制——读者的大脑先被标准结构骗过去，以为这是一篇认真的文章，读到具体内容才发现完全不对。

`OPENERS` 和 `CLAIMS` 也是专门为长文写的两句口癖：

```js
const OPENERS = [
  "首先，我不敢苟同你的观点。",
  "说实话，我不太认同现在主流对这件事的看法。",
  "我跟你讲，这个事很多人从一开始就理解反了。",
  "你先别急着反驳，听我把话说完。",
  "这个问题其实没有大家想的那么复杂。",
  "我研究这个方向有些年头了，说句掏心窝子的话。"
];

const CLAIMS = [
  "{A}就应该{V}{B}，这是最基本的常识。",
  "我个人认为，{A}必须{V}{B}，没有第二种可能。",
  "{A}这个东西，本质上就是{V}过的{B}。",
  "真正懂行的人都知道，{A}是不能{V}{B}的。",
  "{A}和{B}的关系，比大多数人想象的要紧密得多。"
];
```

「我不敢苟同」「没有第二种可能」「真正懂行的人都知道」——**这些是「确信度极高但内容极不靠谱」的组合**，比单纯的胡说更好笑，因为它是「自信地错」。

### 6.3 单句 `genSingle` + `{U}` 接话 `genReply`

单句最简单：抽一个模板，渲染，完事。但它带 `minSlots`，因为只有一句，必须装下全部关键词。

接话最有意思，它是**真的在回应你说的话**：

```js
function genReply(level, userText, sceneKey) {
  const sc = SCENES[sceneKey] || SCENES.any;
  const used = new Set();
  const msgs = [];
  genCtx.cap = 1;

  // 空输入就随机挑一句开场白
  const said = (userText || "").trim() || pick(sc.openers);
  msgs.push({ side:"left", text: said });   // 原样复述你说的话

  const n = 2 + rnd(2);
  for (let i = 0; i < n; i++) {
    const fresh = REPLY_TPL.filter(x => !used.has(x));
    const t = pick(fresh.length ? fresh : REPLY_TPL);
    used.add(t);
    // 关键：把 {U} 换成人话，并且截断
    const body = render(t, { mix:"vp" }).replace(/\{U\}/g, clip(said, 14));
    msgs.push({ side:"right", text: body });
  }
  genCtx.cap = 3;
  return msgs;
}

function clip(s, n) {
  s = s.replace(/[「」""]/g, "").trim();
  return s.length > n ? s.slice(0, n) + "…" : s;
}
```

`{U}` 不在 `render` 里替换，而是**渲染完之后单独替换**。原因很简单：`render` 只认 `{A}`~`{U}` 里那些预定义槽位，`{U}` 是用户的原话，得单独处理。

`clip(s, 14)` 把用户的话截到 14 个字。因为：
1. 用户可能输入一大段，塞进模板会撑爆版面
2. 截断 + 省略号本身就有「引用」的语感

`REPLY_TPL` 只有 7 条，但每条都用 `{U}` 引用用户原话：

```js
const REPLY_TPL = [
  "你说「{U}」，但从{T}的角度看，这本身就违反了{C}的{F}。",
  "关于「{U}」这件事，我只有一个疑问：{A}为什么一直在{V}{B}？",
  "「{U}」这个说法是站不住的，因为{A}的{P}根本没有达到{P2}。",
  "我不太认同「{U}」，{A}明明应该{V}{B}，这一点没什么可商量的。",
  "你有没有想过，「{U}」其实只是{A}在{V}{B}过程中产生的一种错觉。",
  "「{U}」？这说明你还没意识到{C}的{P}已经改变了{D}的{F}。",
  "说到底，「{U}」和{A}根本就不是一个{G}层面的东西。"
];
```

全部是**「先引用你，再否定你」**的结构。这个结构是互联网吵架的经典形态，熟悉感拉满。

## 七、发疯指数：给自己编个评分标准

每次生成完，底下会显示「发疯指数 78 · 横跨 4 个语义域」。

这个分数是**真的算出来的**，不是随便给的随机数：

```js
function scoreText(text, kws){
  // 1. 找出这句话里出现了哪些语义域的词
  const hit = [];
  DOMAINS.forEach(function(d){
    if (LEX[d].some(w => text.indexOf(w) >= 0)) hit.push(d);
  });

  // 2. 算这些域的「语气跨度」
  const vals = hit.map(d => TONE_VAL[TONE[d]]);
  const spread = vals.length ? (Math.max(...vals) - Math.min(...vals)) : 0;

  // 3. 数伪专业术语的个数
  let terms = 0;
  TERM.forEach(t => { if (text.indexOf(t) >= 0) terms++; });

  // 4. 加权计分
  let s = 46 + spread * 12 + Math.min(hit.length, 5) * 4 + Math.min(terms, 3) * 6;
  if (text.length >= 22) s += 8;
  if (text.length >= 40) s += 4;
  if (/[？?]/.test(text)) s += 3;

  // 5. 用户塞的词也算一个「自定义域」
  const hasKw = !!(kws && kws.length && kws.some(w => w && text.indexOf(w) >= 0));
  if (hasKw) s += 7;

  return {
    score: Math.max(55, Math.min(99, Math.round(s))),
    domains: hit.length + (hasKw ? 1 : 0)
  };
}
```

计分规则的物理含义：

| 因素 | 加分 | 为什么 |
|---|---|---|
| 基础分 | 46 | 保底，不让分数太难看 |
| **语气跨度** | 每级 × 12 | 最俗 + 最专业混在一句，是最荒诞的 |
| 语义域数量 | 每个 × 4（最多 5 个） | 跨的域越多越离谱 |
| 专业术语数 | 每个 × 6（最多 3 个） | 术语密集显得「有依据」，反差更强 |
| 长度 ≥ 22 字 | +8 | 短句不够「一本正经」 |
| 长度 ≥ 40 字 | +4 | 长句才有论证感 |
| 有问号 | +3 | 反问句更有攻击性 |
| 命中了用户关键词 | +7 | 用户参与感，算「自定义域」 |

最后 `Math.max(55, Math.min(99, ...))` 把分数夹在 55~99 之间。

**为什么下限是 55？** 因为哪怕一句话很平淡，给个 60 分也比给 30 分让人舒服。这是**心理学不是数学**——打分器的目的是正反馈，不是科学测量。

**为什么上限是 99 不是 100？** 留一分，让人有「还没到极致」的期待。

多句的时候取平均分，域数取最大值：

```js
function scoreAll(msgs, kws){
  const arr = msgs.map(m => scoreText(m.text, kws));
  const avg = arr.reduce((a, b) => a + b.score, 0) / arr.length;
  const domains = Math.max(...arr.map(x => x.domains));
  return { score: Math.round(avg), domains: domains };
}
```

> **这段代码有个我必须承认的偷懒**：它是用 `text.indexOf(word)` 在整句里找词，如果有两个词互为子串（比如「面包」和「面包车」），会误判。对一个玩具来说，这个误差可以接受，我没去优化它。**知道哪里可以偷懒，也是一种工程判断。**

## 八、存图：全篇最麻烦的一块

「存图」是把这个聊天记录导出成一张 PNG。看着简单，实际上这是我花时间最多的地方。

### 8.1 为什么不用 html2canvas 之类的库

因为**整个项目零依赖**。引入一个 200KB 的库，只为了一张图，不值得。而且 html2canvas 对中文断行、字体渲染的处理，还不一定比我手写的好。

所以直接上 `Canvas 2D API`，手动画。

### 8.2 思路：先量后画

不能一边画一边算坐标，因为**画布高度取决于内容高度**，而内容高度得先算出来。所以分两步：

**第一步：量尺寸**

```js
const S = 2;                 // 高清倍数（Retina）
const W = 750;               // 逻辑宽度
const PAD = 46;              // 左右留白
const AV = 64, AVGAP = 18;   // 头像尺寸 / 头像与气泡间距
const BX = 24, BY = 20;      // 气泡内边距
const FS = 31, LH = 53;      // 字号 / 行高
const MAXB = W - PAD * 2 - AV - AVGAP;   // 气泡最大宽度

// 逐条计算每条消息要几行、多宽、多高
const layout = msgs.map(function(m){
  const lines = wrap(m.text, MAXB - BX * 2);
  const tw = Math.max(...lines.map(l => ctx.measureText(l).width));
  const bw = Math.min(MAXB, Math.ceil(tw) + BX * 2);
  const bh = lines.length * LH + BY * 2;
  return { side:m.side, lines:lines, bw:bw, bh:bh };
});

// 总高度 = 头部 + 所有气泡 + 底部
const HEAD = 252, FOOT = 158, GAP = 22;
const bodyH = layout.reduce((s, m) => s + m.bh + GAP, 0);
const H = Math.round(HEAD + bodyH + FOOT);
```

`ctx.measureText()` 是 Canvas 测量文字宽度的方法。**量完才知道该给多宽的盒子**，这是排版的基本功。

**第二步：画**

```js
cv.width = W * S;          // 物理像素 = 逻辑宽度 × 2
cv.height = H * S;
ctx.scale(S, S);           // 关键：缩放坐标系，之后都按逻辑尺寸写
ctx.fillStyle = "#F7F7F2";
ctx.fillRect(0, 0, W, H);
```

`ctx.scale(S, S)` 这一行很重要。画布物理尺寸放大 2 倍，但坐标系也放大 2 倍，于是**后面所有代码都可以按 750 宽来写，不用管高清的事**。这是 Canvas 做 Retina 适配的标准做法。

### 8.3 最难的部分：中文断行

这是整个项目技术上最有意思的地方。

英文断行简单——在空格处断开就行。中文没有空格，**每个字都可能是断点**，但**标点不能出现在行首**（排版规则叫「避头尾」）。

如果你直接按宽度硬切，会出现：

```
意大利面应该拌42号混凝土，这一点没什么可
商量的。
```

看起来还行？那试试这个：

```
意大利面应该拌42号混凝土，这一点没什么可商
，量的。
```

**逗号跑到行首了。** 这在中文排版里是硬伤，一眼就能看出来不对劲。

我的处理：

```js
/* 中文换行：标点不能出现在行首，需要把上一个字一起挪下来 */
const NO_START = "，。、；：？！）》」』""%·";

function wrap(text, maxW){
  const out = [];
  let line = "";

  for (const ch of text) {
    // 加上这个字会超宽？
    if (ctx.measureText(line + ch).width > maxW && line) {
      if (NO_START.indexOf(ch) >= 0 && line.length > 1) {
        // 要把标点放行首了 → 把上一行最后一个字挪下来陪它
        out.push(line.slice(0, -1));
        line = line.slice(-1) + ch;
      } else {
        out.push(line);
        line = ch;
      }
    } else {
      line += ch;
    }
  }
  if (line) out.push(line);
  return out;
}
```

核心是这三行：

```js
out.push(line.slice(0, -1));      // 上一行去掉最后一个字
line = line.slice(-1) + ch;       // 那个字 + 标点，一起开始新行
```

效果：

```
意大利面应该拌42号混凝土，这一点没什么
可商量。
```

嗯……还是有点怪，但至少**标点没在行首**了。这是排版上的正确做法，代价是行尾会稍微短一点。真实的中文排版软件（比如 InDesign）也是这么干的。

`NO_START` 这个字符串里放的全是不能当行首的字符：逗号、句号、顿号、分号、冒号、问号、叹号、右括号、右书名号、右引号、百分号、间隔号。

> **为什么不用更完整的 Unicode 标点集合？**
> 因为这是个玩具，我把最常见的中文标点都列了，够用了。
> 加上 `%` 和 `·` 是因为它们视觉上像标点，跑到行首也难看。
> **够用就停，是零依赖项目的必备美德。**

### 8.4 圆角矩形和手绘头像

Canvas 没有内置的圆角矩形，得自己用 `quadraticCurveTo` 画：

```js
function roundRect(ctx, x, y, w, h, r, corner){
  // corner 指定哪个角是「小圆角」（聊天气泡靠头像那一侧）
  const tl = (corner === "tl") ? 6 : r;
  const tr = (corner === "tr") ? 6 : r;
  ctx.beginPath();
  ctx.moveTo(x + tl, y);
  ctx.lineTo(x + w - tr, y);
  ctx.quadraticCurveTo(x + w, y, x + w, y + tr);
  ctx.lineTo(x + w, y + h - r);
  ctx.quadraticCurveTo(x + w, y + h, x + w - r, y + h);
  ctx.lineTo(x + r, y + h);
  ctx.quadraticCurveTo(x, y + h, x, y + h - r);
  ctx.lineTo(x, y + tl);
  ctx.quadraticCurveTo(x, y, x + tl, y);
  ctx.closePath();
}
```

`quadraticCurveTo(控制点x, 控制点y, 终点x, 终点y)` 是二次贝塞尔曲线。四个角画四次，就是一个圆角矩形。

`corner` 参数是为了做微信那种效果：**靠头像那一侧的角是小圆角，另一侧是大圆角**。这个细节让气泡看起来「有方向感」，是有来源的。

头像也是纯手画的：

```js
function drawFace(ctx, cx, cy, isMe){
  ctx.save();
  ctx.strokeStyle = isMe ? "#2A4A16" : "#3A3A32";
  ctx.fillStyle = ctx.strokeStyle;
  ctx.lineWidth = 3.2;
  ctx.lineCap = "round";
  ctx.lineJoin = "round";

  if (isMe) {
    // 我：一个圆 + 一道弧 = 人形剪影
    ctx.beginPath(); ctx.arc(cx, cy - 5, 8.5, 0, Math.PI * 2); ctx.stroke();
    ctx.beginPath(); ctx.arc(cx, cy + 17, 12, Math.PI * 1.12, Math.PI * 1.88); ctx.stroke();
  } else {
    // 对方：两只耳朵 + 圆脸 + 两只眼睛 = 猫
    ctx.beginPath(); ctx.moveTo(cx - 13, cy - 1); ctx.lineTo(cx - 10, cy - 15); ctx.lineTo(cx - 1, cy - 7); ctx.stroke();
    ctx.beginPath(); ctx.moveTo(cx + 13, cy - 1); ctx.lineTo(cx + 10, cy - 15); ctx.lineTo(cx + 1, cy - 7); ctx.stroke();
    ctx.beginPath(); ctx.arc(cx, cy + 2, 12, 0, Math.PI * 2); ctx.stroke();
    ctx.beginPath(); ctx.arc(cx - 4.5, cy - 1, 1.7, 0, Math.PI * 2); ctx.fill();
    ctx.beginPath(); ctx.arc(cx + 4.5, cy - 1, 1.7, 0, Math.PI * 2); ctx.fill();
  }
  ctx.restore();
}
```

猫头像 = 两个三角形耳朵 + 一个圆脸 + 两个小圆眼睛。人形 = 一个头 + 一段肩膀弧线。**用最原始的几何图形拼**，不用任何图标库或图片资源。

这也是零依赖的一部分：**图标都是手画的 SVG/Canvas 路径，不加载任何外部文件。**

### 8.5 导出下载

```js
cv.toBlob(function(blob){
  const url = URL.createObjectURL(blob);
  const a = document.createElement("a");
  a.href = url;
  a.download = "知识搅拌机_" + Date.now() + ".png";
  document.body.appendChild(a);
  a.click();
  document.body.removeChild(a);
  setTimeout(() => URL.revokeObjectURL(url), 4000);
  showToast("已保存到下载目录");
}, "image/png");
```

这是浏览器里「生成文件并让用户下载」的标准套路：

1. `toBlob` 把画布转成二进制图片（比 `toDataURL` 省内存，不会生成超长 base64 字符串）
2. `URL.createObjectURL` 把 blob 包成一个临时 URL
3. 造一个隐藏的 `<a download>`，点它
4. **`revokeObjectURL` 释放内存**——这一步不做，反复存图会漏内存

`setTimeout(..., 4000)` 是给浏览器留出下载启动的时间，不能立刻 revoke，否则可能下载失败。

`Date.now()` 拼在文件名里，防止重名覆盖。

## 九、那些看起来不起眼、但决定手感的东西

技术讲完了，讲几个**不涉及算法，但直接影响「用起来爽不爽」**的地方。

### 9.1 打字机效果：让等待变成表演

生成不是一次性把话全贴上去，而是一条一条「冒」出来：

```js
function stream(list, kws, done){
  let i = 0;
  (function step(){
    if (i >= list.length) { updateFade(); done && done(); return; }
    const item = list[i++];
    addMsg(item.side, item.text, true, kws);
    scrollBottom();
    updateFade();
    // 停留时间：句子越长，停越久（但有上限）
    setTimeout(step, 170 + Math.min(item.text.length * 6, 210));
  })();
}
```

`170 + Math.min(item.text.length * 6, 210)` 这个公式：

- 基础 170ms
- 每多一个字加 6ms
- 但最多只加到 210ms（所以实际总间隔在 170~380ms 之间）

**为什么要跟长度挂钩？** 因为长句需要更多时间阅读。如果长短句都是固定间隔，读长句的时候会手忙脚乱，读短句的时候会嫌慢。

**为什么要有上限？** 防止超长句子等太久。用户体验上，「等」这件事不能超过一秒。

这个效果技术上就是 `setTimeout` 递归。但它把「瞬间出结果」变成了「正在被生成」的**表演感**——这是产品体验，不是技术。

### 9.2 复制：三级降级

```js
function copy(text){
  const ok = () => showToast("已复制");
  if (navigator.clipboard && navigator.clipboard.writeText) {
    navigator.clipboard.writeText(text).then(ok).catch(() => { fallbackCopy(text); ok(); });
  } else {
    fallbackCopy(text); ok();
  }
}

function fallbackCopy(text){
  const ta = document.createElement("textarea");
  ta.value = text;
  ta.style.position = "fixed";
  ta.style.opacity = "0";
  document.body.appendChild(ta);
  ta.select();
  try { document.execCommand("copy"); } catch(e){}
  document.body.removeChild(ta);
}
```

`navigator.clipboard` 有两个坑：
1. **Safari 和旧浏览器可能没有**
2. **只在 HTTPS 或 localhost 下可用**，`file://` 打开会失败

所以必须有降级方案：造一个透明的 `<textarea>`，选中，`execCommand("copy")`，删掉。这是上古 API，但兼容性最好。

> 这个项目我是打算双击 `index.html` 直接用的（`file://` 协议）。
> 在 `file://` 下 `navigator.clipboard` **一定不可用**，走的全是 fallback。
> **如果你的项目要离线打开，切图、剪贴板、摄像头这些 API 全都要想好降级方案。**

### 9.3 关键词高亮：先转义，再替换

```js
function esc(s){
  return s.replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;");
}

function highlight(text, kws){
  let html = esc(text);            // ① 先转义
  if (!kws || !kws.length) return html;
  kws.forEach(function(w){
    if (!w) return;
    const safe = esc(w);           // ② 关键词也要转义
    if (html.indexOf(safe) >= 0) {
      html = html.split(safe).join('<mark>' + safe + '</mark>');   // ③ 再替换
    }
  });
  return html;
}
```

**顺序不能反。** 如果先替换成 `<mark>` 再转义，`<mark>` 自己会被转义成 `&lt;mark&gt;`，高亮就失效了。

关键词本身也要 `esc()`，因为用户可能输入 `<script>` 之类的东西。虽然这里只是拼进 `innerHTML`，但**养成「任何用户输入进 HTML 前都转义」的习惯**，是防止 XSS 的第一道防线。

顺带说，真正危险的是 `innerHTML`。这个项目里所有文本都过了一遍 `esc()` 才进 `innerHTML`，所以是安全的。如果图省事直接 `el.innerHTML = text`，就等着被注入吧。

### 9.4 底部渐隐遮罩

聊天卡滚到底部时，最后一行会被卡片边缘「切」得很生硬。加一层渐变遮罩：

```css
.stage.has-overflow::after{
  content:"";
  position:absolute; left:0; right:0; bottom:0; height:56px;
  border-radius:0 0 24px 24px;
  background:linear-gradient(to bottom, rgba(247,247,242,0) 0%, rgba(247,247,242,.86) 46%, #F7F7F2 66%);
  pointer-events:none;      /* 关键：不挡点击 */
  z-index:2;
}
```

用 `::after` 伪元素，不增加 DOM 节点。`pointer-events:none` 保证遮罩不挡住气泡的点击复制。

但只在「内容溢出」时才需要遮罩，所以要用 JS 判断：

```js
function updateFade(){
  const over = $card.scrollHeight > $card.clientHeight + 8;
  $stage.classList.toggle("has-overflow", over);
}
```

`+8` 是个容差，防止因为亚像素误差导致抖动。

### 9.5 手机安全区

iPhone 底部有「小白条」（Home Indicator），如果按钮贴到底会被它挡住。用 `env(safe-area-inset-bottom)` 解决：

```css
.app{
  padding: 22px 18px calc(18px + env(safe-area-inset-bottom));
}
```

为了让这个生效，`<meta viewport>` 里必须有 `viewport-fit=cover`：

```html
<meta name="viewport" content="width=device-width,initial-scale=1,viewport-fit=cover">
```

**这两行要一起写，缺一个都不生效。** 我第一次只写了一个，怎么调都没反应，查了半天。

### 9.6 高度用 `dvh` 不用 `vh`

```css
body{
  height: 100vh;    /* 老浏览器兜底 */
  height: 100dvh;   /* 新浏览器：动态视口高度 */
  overflow: hidden;
}
```

手机浏览器的地址栏可以收起/展开，`100vh` 是按「地址栏展开时」算的，会导致底部内容被地址栏挡住。`100dvh`（dynamic viewport height）会跟着地址栏变化。

写两遍，下面那行覆盖上面那行——老浏览器不认识 `dvh` 会忽略它，新浏览器会用 `dvh`。这是标准的**渐进增强**写法。

## 十、技术栈总结

现在回头看，这个项目用了什么？

**零。**

|---|---|---|
| 框架 | 无 | 原生 DOM API，`document.getElementById` + `addEventListener` |
| 构建工具 | 无 | 没有 `package.json`、没有 `npm install`、没有打包 |
| CSS 框架 | 无 | 手写，约 180 行 |
| UI 组件库 | 无 | 按钮、输入框、胶囊都是原生元素手写样式 |
| 图表库 | 无 | 进度条是 `<div>` + `width` 百分比 |
| 图标库 | 无 | 全部手写 SVG 路径 + Canvas 图形 |
| 图片资源 | 无 | 一个都没有，连 favicon 都是内联的 data URI SVG |
| 字体 | 系统字体 | `-apple-system, PingFang SC, Microsoft YaHei` |

| 存储 | 无 | 不存任何东西，刷新就没了 |
| 依赖总数 | **0** | |

`package.json` 是零字节，我压根没创建过。整个项目就是 **1 个 HTML 文件，48 KB**。

### 这个选择换来了什么

**好的方面：**

1. **部署 = 发给对方。** 微信发过去，对方点开就能用。不需要服务器、不需要域名、不需要备案。
2. **永远能跑。** 不会因为 npm 包升级、CDN 挂掉、浏览器更新而失效。十年后打开还是这样。
3. **看得懂全部代码。** 1058 行，我全知道每行在干什么。用框架的话，出问题要往 node_modules 里挖。
4. **改一行就生效。** 没有编译等待，保存刷新，两秒钟看到结果。

**代价：**

1. **所有东西都要手写。** 断行、圆角、头像、剪贴板降级……每一样都得自己来。
2. **代码无法复用。** 下一个项目还得重写一遍。
3. **没有工程化。** 单人项目还行，两个人同时改就崩了。

**对一个 48KB 的玩具来说，这个交换非常划算。** 但如果这是要维护三年的产品，我会毫不犹豫上框架。

> 技术选型不是「哪个更先进」，是「这个规模配哪个最合适」。
> **拿造火箭的工具做玩具车，和拿玩具车的工具造火箭，都是错的。**

## 十二、如果重做一次

三个我会改的地方：

**1. 句模应该单独成一个 JSON 文件。**
现在句模和逻辑混在一起，加句子要改 HTML。分离出来，别人也能贡献句子。

**2. 词库应该支持用户自定义。**
现在词库是写死的。如果能加一个「我的词库」输入框，让用户塞自己行业的词（「我们公司的 KPI」「我们的代码评审」），荒诞感会翻倍——因为**熟人梗永远比通用梗好笑**。

**3. 发疯指数应该真的做一次统计。**
现在公式里的系数（46、12、4、6……）是我拍脑袋定的。更严谨的做法是：收集一批真人评分，做个线性回归，让系数从数据里长出来。但这需要真实用户数据，现在只有我自己，只能拍脑袋。

> 这三条都是「上到下一个量级」才需要的东西。
> **在当前规模下不做，是对的。** 这就是前面说的「简洁优先」。

## 十三、最后

这个项目技术上没有任何难度。没有算法、没有数据结构、没有架构设计。

它所有的价值都在**一个判断**上：

> **荒诞不来自随机，来自「语法正确」和「语义离谱」之间的落差。**

想清楚这一点，剩下就是攒词、写句子、调手感。而这三件事，**都不能自动化**——你得自己知道「屁股」和「面包」放一起好笑，而「膝盖」和「面包」放一起就不好笑。

这也回答了一个问题：**AI 时代还该不该手写这种东西？**

该。因为这个项目的核心不是生成，是**品味**——什么词配什么词好笑，什么句式听起来一本正经，什么节奏读起来舒服。这些是数据和算法给不了的。

模型能写诗，但它不知道「拌42号混凝土」为什么好笑。
