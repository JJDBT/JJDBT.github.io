# 我做了一个「竞赛罗盘」：把 1600 场大学生赛事装进一张日历

> 一个大学生做的小工具，用来解决「我该参加什么比赛、什么时候报名」这个每年都会踩一次的坑。
> 这篇文章讲清楚它为什么长这样、用了什么技术、以及踩过哪些坑——踩坑部分大概是最有用的。

---

## 一、先说问题：我到底在解决什么

大一大二的时候，我错过过至少三个比赛。

不是不想参加，是**根本不知道**：报名窗口在一月份，而我四月才听说这个比赛。学校的通知靠群消息，聚合平台列了几千条赛事，但每一条都只写「每年 3 月」，没有准确的报名起止日。

所以这件事有三个独立的难点：

1. **信息散**：赛事分散在几十个官网、聚合站、学校通知里，没有一个地方能一次看完。
2. **时间糊**：绝大多数赛事只写「每年 3-5 月报名」，不写具体哪天。你想设个提醒，都不知道设在哪天。
3. **不会选**：知道你该打什么比赛，比知道有哪些比赛难得多。同样是计算机专业，想保研的和想就业的，该打的比赛完全不同。

于是我做了 **竞赛罗盘**：输入你的专业、年级、目标，它给一条从大一排到毕业的参赛路线，并把每场比赛的报名/比赛时间放进一张日历，可以订阅到手机。

## 二、一句话讲清架构

它不是什么复杂系统，甚至可以概括成一句话：

> **一个 FastAPI 后端 + 一个 Vue 前端 + 一个 SQLite 数据库文件，全部跑在一台 2 核 2G 的云服务器上。**

```
┌─────────────────────────────────────────────────────┐
│  用户浏览器（手机 / 电脑）                             │
│  Vue 3 单页应用 + Service Worker（PWA，可装到桌面）      │
└───────────────────────┬─────────────────────────────┘
                        │ HTTPS（nginx 反代）
┌───────────────────────▼─────────────────────────────┐
│  nginx：443 终结证书 / 8080 跳转 / gzip 压缩           │
└───────────────────────┬─────────────────────────────┘
                        │ 127.0.0.1:8000（只监听本机）
┌───────────────────────▼─────────────────────────────┐
│  FastAPI（uvicorn，单进程）                           │
│  ├── 鉴权：JWT + bcrypt                              │
│  ├── 赛事库 / 收藏 / 日历 / 订阅                      │
│  ├── AI 规划引擎（工具调用 + 知识库 + 反编造校验）      │
│  └── 官网日期抓取（Scrapling + 严格抽取）              │
└───────────────────────┬─────────────────────────────┘
                        │ SQLAlchemy ORM
┌───────────────────────▼─────────────────────────────┐
│  SQLite（compass.db，单文件，约 1.2MB）                │
└─────────────────────────────────────────────────────┘
```

几个刻意的选择：

- **不前后端分离部署**。前端 build 成静态文件，直接由 FastAPI 托管，省掉一个静态服务器，也省掉跨域配置。
- **不用 Docker**。一台机器、一个服务、一个数据库文件，`systemd` 管进程就够了。多一层容器只会让排查问题更绕。
- **数据库不单独装**。SQLite 就是文件，备份等于 `tar` 一个文件，迁移等于 `scp` 一个文件。

## 三、技术栈：选了什么，为什么

先说结论表，再逐条解释。

| 层 | 选了什么 | 版本 | 一句话理由 |
|---|---|---|---|
| 前端框架 | Vue 3 | 3.5 | 中文资料最多，模板语法对新手友好 |
| 构建工具 | Vite | 7 | 启动/打包都快，配置几乎为零 |
| UI 组件 | Element Plus | 2.11 | 表格、表单、弹窗开箱即用，省掉一半样式工作 |
| 状态管理 | Pinia | 3.0 | Vue 官方推荐，比 Vuex 清爽 |
| 路由 | Vue Router（hash 模式） | 4.5 | hash 模式不需要后端配 rewrite |
| 日历 | FullCalendar | 6.1.22 | 月/列表视图、滑动、事件点击都是现成的 |
| HTTP | axios | 1.13 | 拦截器统一处理 token 和错误提示 |
| 后端框架 | FastAPI | ≥0.110 | 自动生成接口文档，类型提示即校验 |
| ORM | SQLAlchemy 2.0 | ≥2.0 | 用 Python 对象操作数据库，不手写 SQL |
| 数据库 | SQLite | 内置 | 单机项目，零运维 |
| 鉴权 | python-jose + bcrypt | — | JWT 无状态登录；密码只存哈希 |
| 抓取 | Scrapling | 0.5.1 | 带浏览器 TLS 指纹，能过一部分反爬 |
| 部署 | nginx + systemd + Let's Encrypt | — | 免费证书 + 进程守护 |

### 为什么前端选 Vue 而不是 React

没有技术高下，只有取舍：Vue 的 `.vue` 单文件组件把「结构 / 逻辑 / 样式」放在一个文件里，改一个页面只需要开一个文件；React 的 JSX 对没写过前端的人更劝退。这个项目一共 13 个前端文件，单文件组件的优势很明显。

### 为什么数据库用 SQLite 而不是 MySQL / PostgreSQL

因为**数据量和并发都小到可以忽略**：1664 场赛事、个位数用户、一天几百次请求。SQLite 足够，而且：

- 没有服务要启动，没有端口要开
- 备份 = 复制一个文件
- 本地开发和线上完全一致，不会出现「本地好好的线上报错」

代价是并发写入会锁库。真到几百人同时用的规模，再换 PostgreSQL 也就改一个连接字符串的事（SQLAlchemy 的好处）。

### 为什么日历用 FullCalendar，而不是自己画一个

我一开始是自己画的月历网格：

```
for 每个格子:
    找出这个格子里的事件
    渲染成色块
```

两周后我放弃了。原因不是画不出来，是**画出来的东西要自己实现所有交互**：滑动切月、事件太多折叠成「+3 more」、点日期弹当天的列表、键盘无障碍、手机端触控……每一项都要写一堆边界条件。

换成 FullCalendar 后，这些全部是配置项。**这个决定省了我至少三天。**

代价是：它有自己的 DOM 结构和 CSS，想改样式得按它的规矩来（后面踩坑部分有详细记录）。

### 为什么抓取用 Scrapling 而不是 requests

普通的 `requests` 发出去，`TLS 指纹`是 Python 的，很多网站一眼就看出「这不是浏览器」，直接返回 403 或者假的空页面。

Scrapling 底层是 `curl_cffi`，它会**模仿 Chrome 的 TLS 握手特征**，在网站看来跟真浏览器差不多。实测抓数学建模官网，`requests` 有时候被挡，Scrapling 稳定通过——但两者耗时差不多（1~3 秒）。

不过我没有只用 Scrapling，而是做了一个**降级链**：

```python
try:
    page = Fetcher.get(url, impersonate="chrome")   # ① 优先：带指纹
    if page.status == 200 and 正文够长:
        return page.markdown()
except Exception:
    pass

# ② 兜底：普通请求，保证「抓不动也不能整个接口 500」
r = requests.get(url, headers={"User-Agent": UA})
```

**降级比选型更重要**。抓取这种东西，任何一条路都有 5% 的失败率，只留一条路就是把 5% 变成 100%。

## 四、整个项目最有意思的设计：日期的三种状态

这是我觉得这个项目里最值得讲的一个设计决定。

### 问题

我从聚合站抓了 3157 条赛事，清洗后剩 1664 条。问题是：**其中 98% 没有准确的报名起止日**。

聚合站自己也不写。它们写的是「每年 3-5 月」「3 月中旬」。

那怎么办？三个方案：

| 方案 | 结果 |
|---|---|
| A. 把「每年 3 月」当成 3 月 1 日 | 日历上会显示假日期，用户按它准备会误事 |
| B. 没有确切日期就不显示 | 日历 98% 是空的，等于没做 |
| C. **承认日期有精度差异，分三态存** | 日历上显示「报名窗口」而不是「某一天」 |

我选了 C。

### 具体怎么存

`contests` 表里有两个相关字段：

```sql
date_kind  TEXT   -- 'exact' | 'pattern' | 'none'
months     TEXT   -- 如 "3-5,9"，表示报名在 3~5 月、比赛在 9 月
```

- `exact`：有确切日期，`reg_open`/`reg_close` 是真实的日子
- `pattern`：只知道月份规律，日历上画成**一个跨月的色带**，标注「预计」
- `none`：连月份都不知道，只存在于赛事库里，不进日历

前端渲染时按状态用不同样式：`exact` 是实心色块，`pattern` 是浅色带虚线的色带。用户一眼就知道哪些是确定的、哪些是推测的。

### 这个设计带来的另一个好处

后来加了「AI 去官网抓准确日期」的功能，抓到的日期直接**把 `pattern` 升级成 `exact`**，不用改任何数据结构。三态模型天然容纳「信息逐渐变准」这个过程。

### 用户的收藏日期优先

还有一层：用户手动填的日期 > 抓来的确切日期 > 月份规律。

`pick_items` 表（用户收藏的比赛）里也有 `reg_open`/`reg_close`/`event_start`/`event_end`。生成日历时的合并逻辑：

```python
effective = {
    "reg_open":     pick.reg_open     or contest.reg_open,
    "reg_close":    pick.reg_close    or contest.reg_close,
    "event_start":  pick.event_start  or (从 months 推算),
    "source":       "manual" | "exact" | "pattern",
}
```

`source` 字段很重要——界面上要能告诉用户「这个日期是你自己填的」还是「我们猜的」。

## 五、AI 规划：不是聊天机器人，是「表单 → 一次性出结果」

这是项目里争议最大的地方，我改过三版。

### 版本一：聊天

用户：「我大二，计算机，想保研，该打什么比赛？」
AI：「你好！建议你参加……」
用户：「那 ACM 呢？」
AI：「ACM 是……」

**放弃原因**：用户不知道该说什么。问「我该打什么比赛」，信息量太少，AI 只能给泛泛的答案；要得到好答案，用户得自己想到「哦我应该告诉它我每周有多少时间、我数学好不好、我想去哪个城市」——**而用户不会想到这些**。

### 版本二：表单

把该问的都做成表单：专业、年级、目标（保研/就业/考研/出国/兴趣）、每周可投入时间、现有基础、已获奖项、英语水平、目标城市、预算……

用户填完点一下，AI 一次性输出一条完整路线。

**这个版本对了**。原因很简单：**表单会提示用户该给什么信息，聊天不会**。

### 版本三：表单为主 + 聊天做补充

保留表单，但生成结果后给一个输入框：「还有想说的？比如『不想去北方』」。

这句话会被并进**用户画像**（存在 `users.profile_json` 里），然后带着上一条结果重新生成。

> 所以它现在的定位是：**一次性生成器，聊天只是补充记忆的入口**。
> 用户填得越全，一次出来的结果越好。

### AI 怎么不编造比赛

这是最关键的工程问题。大模型最擅长的事情之一就是**编造一个听起来很像真的比赛**（「全国大学生人工智能创新挑战赛」——查无此赛）。

我的做法是**给模型工具，但只允许它推荐数据库里真实存在的**：

```python
TOOLS = [
    "search_contests",   # 查赛事库（1664 条真实赛事）
    "list_exams",        # 查证书类考试（四六级/软考/教资/考研…）
    "contest_detail",    # 看某场比赛的完整信息
    "web_search",        # 联网搜（Bing，不需要额外 Key）
]
```

模型可以自由调用这些工具，但**最终输出的每一场比赛都必须带 `uid`**。后端拿到响应后做一次校验：

```python
for item in result["contests"]:
    if item["uid"] not in 数据库里真实存在的uid集合:
        丢弃   # 编造的直接扔掉
```

这一步叫**反幻觉校验**。没有它，AI 规划的产品是不可信的——用户按一个不存在的比赛准备三个月，那是灾难。

### 领域知识库

光靠 1664 条赛事不够。区块链、网安、集成电路这些新兴方向，库里覆盖很薄。

所以单独维护了一个 `knowledge.py`（663 行，纯 Python 字典）：每条出路怎么打、每个年级该干什么、每个方向有哪些代表性赛事、哪些是「水赛」不值得去。

生成规划时按用户的方向**选择性注入**系统提示词——不是全塞进去（会挤爆上下文），而是按目标筛。

## 六、AI 去官网抓准确日期

日历最大的痛点是「不知道确切日期」。所以做了一个功能：**点一下，AI 去官网把日期抓回来**。

### 三步链路

```
① 抓页面     Scrapling 优先 → requests 兜底 → 统一转成干净 Markdown
      ↓
② 严格抽取   模型只做一件事：从这段文字里找日期，没写就返回 null
      ↓
③ 校验入库   YYYY-MM-DD 格式校验 + 区间倒置自动交换 + 写进用户日历
```

### 为什么模型只能「抽取」，不能「推测」

系统提示词里的硬性规则（原文摘录）：

```
1. 只依据正文，禁止用你自己的常识补全。正文没写的字段返回 null，不要猜。
2. 日期一律 YYYY-MM-DD。正文只写「3 月 1 日」但没写年份的，用正文里能确定
   的年份；推不出来就 null。
3. 正文给的是一个区间，拆成 reg_open / reg_close。
4. 若正文出现「下一届尚未公布」「敬请期待」等，返回 found=false。
5. quote 必须是正文原文里的片段（≤80 字），用来让人核对，不要改写。
```

第 5 条是**给自己留证据**：返回的日期必须附一段官网原文，用户在界面上能看到「我们是从这句话里读出来的」。这样即使读错了，用户也能一眼发现。

### 抓不到的时候说什么

抓不到不是失败，是常见情况。所以接口区分两种返回：

| 情况 | HTTP | 前端表现 |
|---|---|---|
| 抓到了 | 200 + `status: ok` | 提示「已抓到：比赛 9/10 起」，附官网原文 |
| 抓到了但官网没写日期 | 200 + `status: unknown` | 弹窗「这场还没有准确信息 / 页面几乎没抓到正文（可能要登录或纯前端渲染）」 |
| 官网打不开 | 502 | 「打不开这个官网（域名解析或连接失败）」 |
| 没配 AI | 400 | 「AI 还没配置，抓不了」 |

**空手而归也要说清楚为什么**，比静默失败好得多。

实测数据：

| 官网 | 结果 | 耗时 |
|---|---|---|
| 数学建模官网 mcm.edu.cn | ✅ 抓到 2026-09-10 | 4.8 秒 |
| CCPC ccpc.io | ❌ 纯前端渲染，没正文 | 1.0 秒 |
| ICPC icpc.global | ❌ 同上 | 2.1 秒 |
| 智能汽车竞赛 | ❌ 域名连不上 | — |

**四个里只成功一个**——这就是真实世界的抓取成功率，任何声称「稳定抓取全网赛事日期」的工具都在骗人。

## 七、日历：合并三种数据源

`/api/my-calendar` 是这个项目逻辑最密集的接口。它要把三种数据合成一份日历：

```
用户手动填的日期（最准，用户自己负责）
        ↓ 覆盖
AI 从官网抓的确切日期（较准，附原文证据）
        ↓ 覆盖
月份规律推算的窗口（最模糊，标注「预计」）
```

输出结构：

```json
{
  "effective": {
    "reg_open": "2026-11-01",
    "reg_close": "2026-11-08",
    "event_start": "2026-11-14",
    "event_end": "2026-11-15",
    "source": "manual",
    "source_name": "你自己填的"
  },
  "missing_time": false
}
```

`missing_time: true` 的比赛会单独列在「待补时间」里，每行后面跟着「AI 抓日期」按钮——**把「不知道」变成「可以去查」**，而不是藏起来。

合并之后的样子（这是真实截图，同一个月的赛事按类型用不同颜色）：

| 蓝 | 报名开始 | 提醒你「可以报了」，不紧急 |

| 橙 | 比赛开始 | 要准备了 |
| 灰 | 比赛结束 | 信息性，压低存在感 |

## 八、PWA 和 Service Worker：为了让日历能装到手机上

### 为什么要 PWA

大学生用手机多。能「添加到主屏幕」、点开就像 App，比记网址体验好太多。

PWA（渐进式 Web 应用）就是干这个的：一个 `manifest.webmanifest`（告诉浏览器图标、名字、主题色）+ 一个 Service Worker（一个在浏览器后台运行的脚本，可以拦截网络请求、缓存资源）。

### Service Worker 做了什么

```js
// 导航请求（打开页面）：网络优先，断网时回退到缓存的首页
if (request.mode === 'navigate') {
  event.respondWith(fetch(req).catch(() => caches.match('/index.html')))
}

// 接口请求：只走网络，绝不缓存（数据必须最新）
if (url.pathname.startsWith('/api/')) {
  event.respondWith(fetch(req).catch(() => 假错误响应))
}

// 带哈希的静态资源：缓存优先（文件名变了说明内容变了）
if (url.pathname.startsWith('/assets/')) {
  event.respondWith(caches.match(req).then(r => r || fetch(req)))
}
```

这三条规则的差别，就是「哪些东西可以旧、哪些必须新」的答案。

## 九、踩坑记录（这一节大概最有价值）

### 坑 1：日历整个白屏，控制台一个错都没有

装了 FullCalendar 之后，`<FullCalendar />` 渲染出来是**一片空白，没有任何报错**。

排查了半天发现：`package.json` 里主包是 `6.1.22`，但 `@fullcalendar/vue3` 被 npm 解析成了 **7.1.4**——大版本不一致，Vue 组件内部调用的 API 在 6.x 里不存在，异常被吞掉了。

**教训**：给一组强耦合的包装依赖时，把所有包的版本显式钉死：

```bash
npm install @fullcalendar/vue3@6.1.22
```

以及：**白屏 + 无报错，优先怀疑版本不匹配**。

### 坑 2：改不动 FullCalendar 的按钮颜色

想改工具栏按钮的颜色，写了样式没反应：

```vue
<style scoped>
.fc-button { background: #2f5bff; }   /* 无效 */
</style>
```

原因：`scoped` 会给选择器加上 `[data-v-xxx]` 属性，编译成 `.fc-button[data-v-1204c66a]`，而 FullCalendar 的 DOM 是它自己在运行时生成的，**永远不会带这个属性**。

**解法**：把覆盖样式放到一个**不带 scoped** 的 `<style>` 块里，并用父容器限定作用域：

```vue
<style>              /* 注意：没有 scoped */
.fc-wrap .fc .fc-button-primary:not(:disabled) { background: #2f5bff; }
</style>
```

验证方法很实在：打包后去 `dist/assets/*.css` 里搜 `fc-button`，确认没有 `[data-v` 后缀。

### 坑 3：Service Worker 把「服务器连不上」说成「你没网」

用户报「打开就显示网络离线」，但我查日志：**他的请求全是 200**，服务器好好的。

问题出在我自己写的一行兜底：

```js
event.respondWith(fetch(req).catch(() =>
  new Response(JSON.stringify({ detail: '当前离线，请检查网络' }), { status: 503 })))
```

任何原因导致的请求失败——服务器重启、手机切后台把请求掐断、网络抖一下——都会被翻译成「你没网」。**这句文案把排查方向彻底带偏了**，用户会去检查自己的 WiFi，而真正的问题在服务器。

**教训**：错误提示不要替用户下结论，要把**现象**说清楚。改成了：

```js
const reallyOffline = navigator.onLine === false
detail: reallyOffline ? '你这边好像没网了' : '连不上服务器（可能正在重启），稍后重试'
```

### 坑 4：改了代码，用户看到的还是旧版本

`sw.js` 没有设置 `Cache-Control: no-cache`，浏览器把旧文件缓存住了，**新的 Service Worker 永远装不上**。用户一直跑旧逻辑，你在服务器上怎么改都没用。

同时还有第二个问题：新 SW 接管后，页面里跑的仍然是旧 JS，要手动刷新才生效。

**两处都补上**：

```python
# 后端：shell 文件必须回源校验
FileResponse(target, headers={"Cache-Control": "no-cache, must-revalidate"})
```

```js
// 前端：注册时禁止走 HTTP 缓存 + 接管后自动刷新一次
navigator.serviceWorker.register('/sw.js', { updateViaCache: 'none' })
navigator.serviceWorker.addEventListener('controllerchange', () => location.reload())
```

### 坑 5：后端直接暴露在公网

部署时图省事写了：

```bash
uvicorn main:app --host 0.0.0.0 --port 8000
```

`0.0.0.0` 意味着**监听所有网卡**，公网可以直接访问 `http://服务器IP:8000`，绕过 nginx 的 HTTPS——**用户的密码是明文在网络上传输的**。

我是用 `curl http://IP:8000/api/stats` 返回 200 才发现的。

**正确做法**：只监听本机，让 nginx 做唯一入口。

```bash
uvicorn main:app --host 127.0.0.1 --port 8000
```

### 坑 6：主包 1.1MB 原样发给访客

页面加载很慢，查下来发现 nginx 的 `gzip on;` 是开着的，但 `gzip_types` 是注释掉的——**默认只压 HTML，JS/CSS 完全不压**。

而且还有第二层坑：`gzip_proxied` 默认是 `off`，意味着**经过反向代理的响应一律不压缩**。这个项目全是 `proxy_pass`，等于一个字节都没压。

修完（加上 `gzip_proxied any` 和 `gzip_types ... text/javascript`）后的对比：

| | 之前 | 之后 |
|---|---|---|
| 主包体积 | 1,104,127 字节 | **365,706 字节** |
| 首屏可用 | 几十秒 / 白屏 | **1.1 秒** |

顺便加了静态资源长缓存（文件名带哈希，内容变了文件名就会变，所以可以缓存一年）：

```nginx
location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}
```

### 坑 7：Windows 的 .bat 把中文吃掉了

给一个抓网页的小工具写了启动脚本，用户双击后整屏报错：

```
'ng' 不是内部或外部命令
'w.saikr.com' 不是内部或外部命令
```

原因是 `.bat` 文件存成了 **UTF-8**，而 Windows 控制台按 **GBK** 解析——中文全部变成乱码字节，连命令都被拆断。

**最终解法不是换编码，而是让脚本里一个中文都不出现**：把工具挪到纯英文路径，`.bat` 里只有 ASCII 字符。编码问题就不会再出现。

> 这个坑和我做前端踩的所有坑都不一样：它不是逻辑错误，是**操作系统层面的约定**。跨平台工具最容易被这种东西卡住。

### 坑 8：AI 额度没有每日上限

一开始只做了「每小时 20 次」的限制。但这是**自己掏钱调 API** 的项目，公开之后有人拿脚本刷，一小时 20 次 × 24 小时 = 480 次，账单会很难看。

补上每日额度：

```python
AI_FREE_DAILY = 2      # 免费用户每天 2 次
if user.is_pro:        # 会员不限
    return
```

而且**失败要退次数**——AI 自己超时或者模型报错，不能让用户白扣一次：

```python
_ai_take(user, db)
try:
    result = call_ai()
except Exception:
    _ai_refund(user, db)    # 报错不扣次数
    raise
```

## 十、成本控制：这个项目一个月花多少钱

| 项目 | 花费 |
|---|---|
| 云服务器（2 核 2G） | 约 100 元/月（学生机更便宜） |
| 域名 | 用 `sslip.io` 免费泛解析，0 元 |

| AI 调用 | DeepSeek，一次规划约 0.01~0.03 元 |
| 赛事数据 | 自己抓的，0 元 |

**主要的可变成本是 AI 调用**。所以做了三道闸：每小时 20 次（防狂点）、每天 2 次（防白嫖）、失败退款（防误伤）。

## 十一、部署：四条命令的事

```bash
# 1. 代码丢上去
tar czf - backend frontend/dist | ssh root@服务器 "tar xzf - -C /opt/compass"

# 2. 装依赖（只第一次）
/opt/compass/venv/bin/pip install -r backend/requirements.txt

# 3. 跑数据库迁移（只加字段，不删数据，可重复执行）
/opt/compass/venv/bin/python backend/migrate.py

# 4. 重启
systemctl restart compass
```

`systemd` 负责：开机自启、崩溃自动重启、日志进 journald。

```ini
[Service]
ExecStart=/opt/compass/venv/bin/uvicorn main:app --host 127.0.0.1 --port 8000
Restart=always
```

nginx 负责：HTTPS 证书、gzip、静态资源缓存、以及把 `127.0.0.1:8000` 反代出去。

**为什么用 systemd 而不是 `nohup python main.py &`**：后者机器一重启就没了，进程崩了也不会自己起来，日志还得自己管。systemd 三项全包。

```
① 人工整理种子          73 场「一定有、一定重要」的赛事（白名单）
```

这一步最花时间的不是写代码，是**判断哪些是水赛**。代码能去重、能正则去噪，但「这个比赛值不值得参加」只能人判断。

## 十四、如果重来，我会改什么

1. **一开始就用 FullCalendar**，别自己画日历。手写网格的维护成本远超预期。
2. **一开始就上 `127.0.0.1` 绑定 + gzip 配置**。这两个都是「部署完才发现」的坑，但一秒钟就能改对。
3. **错误提示先想清楚「这句话会让用户去检查什么」**。说「你没网」会让用户查 WiFi，说「服务器连不上」才会让用户等一会儿或者找我。
4. **日期三态模型应该一开始就有**。我是先存了假日期（`2026-06-30` 这种月末占位），后来才改成三态——中间那段假数据差点进了用户的日历。
5. **AI 的额度限制应该和 AI 功能同时上线**。我是先做完功能，公开前才补的限制。

## 十五、给想自己做一个的同学

如果你也想做一个类似的工具，我的建议是：

**先做最小可用的那一块**。这个项目最初只有「赛事库 + 收藏 + 日历」三个页面，没有 AI、没有抓取、没有 PWA。AI 是第三周才加的。

**数据比功能重要**。1664 条清洗干净的赛事，价值远大于再多一个花哨的页面。而且清洗数据这件事没法让 AI 全自动做——它需要你知道「这个比赛到底算不算水赛」。

**别怕删代码**。我做 AI 规划做了三版（聊天 → 表单 → 表单+补充），前两版全部删掉了。删掉的 400 行代码不是浪费，是搞清楚「什么样的交互才对」的学费。

**功能上线前想好成本**。AI 是唯一会随用户增长而变贵的部分，限流不是「加个功能」，是**必须有的基础设施**。
