## 一、先说说这玩意儿到底在干嘛
我和 agent 做的这版半自动翻转外语小程序，**内涵其实特别朴素**：

```plain
先乱输一通 → 逼小程序把正确答案显示出来 → OCR 认出来 → 自动一个个字母敲进去
```

跟史师傅最初那版相比，**主体思路一点没变**。真正难的地方不在"打字"这一步，而在于：

> **发出去之后，别人的手机跟我的不一样。**
>

同一套写死的坐标，在我手机上点得稳稳的，换了台屏幕宽高比不同的手机，轻则点空，重则误触到「返回」「删除」，甚至一屁股点到广告上。这就是这个项目 90% 的痛苦来源。

我这版的核心增量是**加了 Shizuku 来模拟 root 权限**，做到**开始拼写之前先自动适配手机**（标定键盘、换算坐标），而不是硬编码一套数字到处跑。

至于其他题型（听力、语法、阅读），因为**没有错误次数限制**，就可以请出计算机科学里最浪漫的定理：

> **无限猴子定理** —— 让一只猴子在键盘上无限随机敲击，只要时间足够长，它一定能敲出莎士比亚全集。
>
> 同理，无限连点下去，总能点完。
>

理论成立。那就让 agent 开始实践吧。

## 二、第一道坎：为什么点一下会出两个字母
整套东西最早跑起来的时候，最玄学的问题是：

```plain
我让它敲 d-e-p-e-n-d-e-n-t
它给我敲出 ddeeppend
```

日志里明明写着「点了一次 d」，坐标也对，**但输入框里就是两个 d**。

于是我们开始了漫长的排查。以下是**真实发生过的**排查过程（按时间顺序）：

| 猜想 | 验证方法 | 结果 |
| --- | --- | --- |
| 是代码点两次了？ | 翻日志，每次按键只有一条记录 | ❌ 排除 |
| 是延迟太短，事件被合并了？ | 把间隔从 0ms 拉到 60ms | ❌ 照样重复 |
| 是无障碍服务在捣鬼？ | 关掉无障碍再测 | ❌ 还是重复 |
| 是 `MotionEvent` 构造得不对？ | 参数改成和 AOSP 源码一模一样 | ❌ 依旧重复 |
| **是注入路径的问题？** | **用 **`adb shell input tap`** 点同一个键** | ✅ **只出一个！** |


**结论**：

+ 走 **binder 直接调用 **`IInputManager.injectInputEvent`（即"App 自己注入"）→ 键盘算成 **2 次**
+ 走 **shell 的 **`input tap`** 命令** → **1 次**

同样的坐标、同样的时间参数、同样的权限，**小程序那个自绘键盘就是能区分出来**。具体为什么，我们至今没查明白（可能是 WebView 对"非 shell 来源"事件的某种去抖逻辑）。

查不明白就不查了。**既然它认 **`input tap`**，那我们就照着那条能用的路走**：

```kotlin
// 通过 Shizuku 借用 shell 身份，执行真正的 input tap
Shizuku.newProcess(arrayOf("sh", "-c", "input tap $x $y"))
```

**这就是 Shizuku 在这个项目里的第二个用途** —— 不只是"提权"，更是"换一条键盘认的注入通道"。

## 三、第二道坎：怎么适配"别人家的手机"
这就是我一开始说的那个大难题。解决办法分三步：

### 第一步：别写死坐标，改成"相对位置"
以前是 `点击 (838, 1346)`，现在全部改成**归一化坐标**：

```plain
旧：点击 (838, 1346)        ← 只在 1280×2772 上对
新：点击 (65%, 49%)         ← 任何手机都对
```

运行时再乘上本机真实屏幕尺寸。**一份方案，所有手机通用。**

> 这里还踩过一个特别隐蔽的坑：Android 有**两个**"屏幕高度"——  
`displayMetrics.heightPixels`（不含状态栏/导航栏，比如 2620）  
和 `getRealMetrics()` 的真实全屏（2772）。
>
> 我用错了一次，坐标被缩放了 5.5%，**底部的按钮整整偏了 129 像素** ——  
表现为"程序明明在跑，就是点不中"。这种 bug 不看日志根本猜不出来。
>

### 第二步：键盘自己标定
小程序的键盘是自绘的（不是系统输入法），所以位置得靠**OCR 认出来再算**：

```plain
扫描屏幕 → 找到键盘区域的 4 行 → 量出每行 Y 坐标和每个键的间距
→ 存成"键盘画像"（缓存起来，换分辨率才重新标定）
```

为什么不用固定比例？因为不同机型下方键盘的高度占比是不一样的，差一点点就点到隔壁字母去了。

### 第三步：所有取坐标的操作都做成"可以拖"
给用户一个**半透明的可视化编辑浮层**：能看见底下的真实界面，直接在上面摆编号靶标，拖着调到位置就对。

**关键设计**：拖动时用的是

```kotlin
归一化增量 = 拖动位移 ÷ 画布尺寸
```

**完全不涉及屏幕尺寸的任何换算。** 这样"画布多大、有没有状态栏、是不是刘海屏"这些差异，从根上不可能再影响坐标。

## 四、那些让我怀疑人生的 bug
### 1. 「才拼到 21 题，就宣布完成了」
原本的循环写的是：

```kotlin
for (questionNum in 1..25) { ... }   // 25 题
```

问题是：**中间只要有一题卡住重试，页面其实没翻页，但计数照样 +1**。跑满 25 次就宣布"本轮结束"，实际只做了 21 题。

改成**看页面状态**而不是数次数 —— 结果第一版又太激进：开场页面还没加载完，OCR 什么都没扫到，就被判定成"已经不是拼写题了"，**第一题就退出**。

最后定下来的方案很朴素：**不设上限，靠用户手动停**。加一个 200 次的保险丝纯粹防止异常空转。

### 2. 「whatever 那题的答案是 adv」
用户反馈：拼写 whatever 时，程序把答案认成了 `adv`。

一看截图就笑了：

```plain
det.任何事物；不管什么 pron.无论什么；诸
如此类 adj.都，任何 adv.一点儿都不，丝毫
                    ↑ OCR 抓到了这个
提示 whatever
```

原因是我的判定条件太宽松：

```kotlin
word.length in 3..24 && word.any { it != 'a' }   // "adv" 完全符合 ✗
```

`adv` 三个字母、含 d 和 v，一路绿灯。

修法：加一张**词性缩写黑名单**（`n / v / adj / adv / prep / pron / conj / det / aux / num …` 三十多个），这些一律不当答案。

### 3. 「点两下，悬浮窗就消失了」
这个 bug 查了整整一个下午，表现为：点第二次的时候 App 直接闪退。

翻 logcat 的崩溃堆栈，最后一行是：

```plain
java.lang.Process.isAlive(Process.java:259)
  at com.autoswapeng.app.overlay.a$j.b      ← 悬浮窗的点击回调
  at android.view.ViewRootImpl.dispatchTouchEvent
```

我写了一句：

```kotlin
fun isReady() = ready && process?.isAlive == true
```

而这个 `process` 是 **Shizuku 的跨进程代理**，它**不支持标准的 **`isAlive()` —— 一调就抛异常。而这一句恰好是在**UI 线程的点击回调里**执行的，异常没人接，**整个 App 当场去世**。

**教训**：跨进程代理对象不要乱调标准方法；UI 线程的代码路径上一定要有兜底 try/catch。

### 4. 「应用关闭后，悬浮窗就没了」
这个更阴间。日志里明明白白：

```plain
[MainActivity] 应用关闭
   ↓ 之后再也不写日志了
```

看代码：

```kotlin
override fun onDestroy() {
    LogManager.i("MainActivity", "应用关闭")
    LogManager.close()        // ← 把日志文件流关了
    super.onDestroy()
}
```

**但悬浮窗服务跑在同一个进程里！** 用户一切到微信小程序，Activity 销毁 → 日志流被关闭 → 悬浮窗服务下次写日志 → **写已关闭的流 → 抛异常 → 进程崩溃** → 悬浮窗消失。

一个"顺手关掉日志"的动作，把整个后台服务带走了。

### 5. 关于那个失败的 uinput 方案（诚实记录）
既然 shell 的 `input` 命令每次都要起一个进程（约 70ms），我就想走**内核级注入**：通过 `/dev/uinput` 创建一个虚拟触摸屏，直接往内核写事件 —— 理论上只要几微秒。

而且我验证过**权限是够的**（Shizuku 的 shell 身份带 `uhid` 组，`/dev/uinput` 可读写）。

于是一路踩坑，**连剥了八层**：

```plain
① 可执行文件放在 App 私有目录 → shell 读不到
② /sdcard 是 FUSE 挂载 → 没有执行权限位
③ 裸执行二进制 → Shizuku 拒绝，得走 sh -c
④ "已就绪"的判断写成了恒为真 → 每次都跳过复制
⑤ 整条链路卡在 UI 线程 → ANR，被 MIUI 杀掉
⑥ 启动时机太早，通道还没就绪
⑦ 虚拟设备用了"可用高度"而非"真实高度" → 坐标被缩放
⑧ Shizuku 代理不支持 isAlive() → 直接崩溃
```

八层全剥完之后……**我把它删了。**

理由很简单：它要过的关卡太多，**每一关都可能在别人手机上失败**，而普通用户遇到"连点器不工作"，只会得出一个结论——**这软件是垃圾**。

所以最后**只保留最稳的一条路**：Shizuku 的 `input` 命令（就是拼写功能一直在用、并且被实测点中过的那条）。慢是慢点（每步约 70ms），但**它不会莫名其妙失败**。

后来我把整个 `cpp/` 目录和 native 配置都删干净了。**删掉自己辛苦写的代码，比写它更需要勇气。**

## 六、几条血泪总结
**1. 遇到"玄学问题"，先做 A/B 对照实验，别猜。**  
"为什么点一下出两个字母"如果不是我拿 `adb shell input tap` 做了对照，可能到现在还在改 `MotionEvent` 的参数。

**2. 加日志。**  
这次几乎所有 bug 都是日志直接点出来的。特别是那个 `LogManager.close()` —— 没有日志，你只会看到"服务莫名其妙被销毁"。

**3. 跨设备的东西，一律用相对量。**  
绝对像素是万恶之源。改成归一化之后，一整类 bug 直接绝迹。

**4. 不够稳的方案，再快也不要。**  
uinput 快 30 倍，但它有八道关卡；`input` 命令慢，但它只有一道。**用户不会为你的技术先进性买单，他们只会为"能用"买单。**

**5. 该删就删。**  
失败了八个回合的方案，留着只会占地方、留隐患、误导后来的人（包括三个月后的自己）。
